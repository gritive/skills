# Persona-Based Service Testing

고객 페르소나를 정의하고 실제 서비스를 **고객처럼 사용**하여 사용성, PMF(Product-Market Fit), 업무 워크플로우 적합성을 검증하는 스킬.

**핵심 원칙**: 이 스킬은 E2E 테스트가 아니다. "기능이 동작하는가?"가 아니라 **"이 서비스로 실제 업무를 할 수 있는가?"**를 검증한다.

## 호출 범위

기본은 감지된 서비스의 고객 여정 전체다. `project loop #N`이 scope를 전달했으면
`../project/references/issue-scope.md`를 읽고 scope의 요구사항으로 이어지는 사용자 여정만 테스트한다. scope의 모든
요구사항이 최소 한 persona 시나리오의 단계·관측 결과에 대응해야 완료다. 발견은 `scope_additions` 계약으로 반환한다.

## 산출물 디렉토리

`~/.gritive/persona-test/{프로젝트}/{YYYYMMDD-HHMMSS}/`를 쓴다. **세션 시작에 한 번만 만들고 출력된
절대 경로를 기록해 세션 내내 재사용한다** (Bash 호출 간 셸 변수는 유지되지 않는다). 경로를 잃었으면
그 프로젝트의 **가장 최근 디렉토리**를 찾아 재사용한다 — 산출물이 흩어지지 않게.

```bash
D=~/.gritive/persona-test/$(basename "$(git rev-parse --show-toplevel 2>/dev/null || pwd)")/$(date +%Y%m%d-%H%M%S)
mkdir -p "$D" && echo "$D"
```

**이 디렉토리는 지워지지 않는다 — 그것이 임시 디렉토리 대신 쓰는 이유다.** 스크린샷·리포트는 나중에
참조할 근거이므로 **보존이 기본값이고, 저장 여부나 경로를 사용자에게 묻지 않는다.** 저장소 밖 고정
경로라 대상 프로젝트를 오염시키지 않고, 묻지 못하는 실행에서도 그대로 남는다 — 보존을
`degraded`에 적을 일이 없다. 사용자가 다른 경로를 지정하면 그것을 쓴다.

**리포트는 `report.md`로 남긴다** — 대화 출력이 원본이고 이것은 나중에 참조할 사본이다. 스크린샷과
로그도 여기에 둔다.

## 묻지 못하는 실행 — 강등 규약

subagent에는 `AskUserQuestion`이 없다(예: `project loop`이 dispatch한 경우). 사용자에게 물어야 할
항목을 못 받은 채 도는 실행은 아래 표대로 처리하고, 강등한 것은 무엇을 어떻게 강등했는지
`degraded`에 적어 반환한다. 제안하고 기다리지 않는다.

| 못 받은 것 | 처리 |
| --- | --- |
| 테스트 대상 인터페이스 | **감지된 전부**를 대상으로 진행하고 `degraded`. 감지된 것이 하나도 없으면 `blocked` — 테스트할 대상이 없는 것이지 강등이 아니다 |
| 인터페이스 URL/명령어 | 저장소에서 찾는다(README 실행 절, `package.json` scripts, compose 파일). 못 찾으면 **테스트할 대상이 없으므로 `blocked`** |
| 주요 사용자 역할 | 제품 스펙·코드의 권한 모델에서 추정하고 `degraded`에 근거를 적는다 |
| 페르소나 정의 | 제품 스펙과 코드의 권한 모델만으로 3-5개를 직접 정하고 `degraded`에 적는다 |
| **테스트 계정** | **강등하지 않는다.** 인증이 필요한 서비스에서 계정 없이 도는 것은 강등이 아니라 **다른 테스트**다 — 로그인 화면만 보고 "Friction 발견"을 만들어 낸다. 인증 없이 닿는 범위가 없으면 `blocked`, 있으면 **비로그인 범위만 테스트했다고 `degraded`에 명시**하고 `coverage=partial`로 반환한다 |

산출물 보존은 이 표에 없다 — 저장소 밖 고정 경로라 묻지 않고 그대로 남는다(위 절).

## Phase 1: 준비

### 1-1. 테스트 대상 인터페이스 선택

사용자에게 테스트할 인터페이스를 확인한다. 복수 선택 가능.

| 인터페이스 | 설명                   | 도구           |
| ---------- | ---------------------- | -------------- |
| `web`      | 브라우저 기반 웹 UI    | 사용 가능한 브라우저 자동화 도구 |
| `cli`      | CLI 명령어             | Bash tool      |
| `mcp`      | MCP 도구 직접 호출     | MCP tools      |
| `api`      | REST/GraphQL API       | Bash (curl)    |
| `plugin`   | hook/plugin 워크플로우 | Write + Bash (임시 파일) |

- 복수 선택 시 각 인터페이스를 **독립적으로** 테스트
- `--cross` 옵션 추가 시 인터페이스 간 **크로스 시나리오**도 실행

### 1-2. 프로젝트 설정 로딩

**CLAUDE.md에서 `Persona Test` 섹션을 찾아** 프로젝트별 설정을 로딩한다.

찾아야 할 정보:

- **인터페이스 URL/명령어**: 각 인터페이스의 접속 주소 또는 실행 명령
- **테스트 계정**: 계정 정보 파일 위치 (예: `docs/test-accounts.md`)
- **제품 스펙**: 제품이 해결하는 문제와 핵심 가치 문서
- **프로젝트 페르소나**: 미리 정의된 페르소나 (있으면 사용, 없으면 Phase 2에서 생성)

CLAUDE.md에 설정이 없으면 사용자에게 직접 확인:

1. 서비스에 어떤 인터페이스가 있는가?
2. 테스트 계정은 어디에 있는가?
3. 주요 사용자 역할은 무엇인가?

> 프로젝트 관리자를 위한 CLAUDE.md 설정 가이드: `references/claude-md-setup.md` 참조

## Phase 2: 페르소나 정의

### 좋은 페르소나의 조건

- 서비스의 **다른 측면**을 사용하는 역할 (예: 관리자 vs 실무자)
- **구체적인 업무 목표**를 갖고 있음 (예: "오늘 해야 할 3개 작업을 파악하고 하나를 완료 처리")
- 각 페르소나마다 고유한 **pain point 가설**이 있음
- "오늘의 시나리오"는 3-7단계의 현실적 업무 흐름
- **기술 수준과 인내심을 명시한다** (예: `비기술·낮음`, `개발자·높음`)

### 페르소나 템플릿

| ID  | 이름 | 역할 | 기술수준·인내심 | 업무 목표 | 오늘의 시나리오 | 핵심 검증 |
| --- | ---- | ---- | --------------- | --------- | --------------- | --------- |

CLAUDE.md에 프로젝트 페르소나가 정의되어 있으면 사용한다. 없으면 제품 스펙과 사용자 입력을 기반으로 3-5개 페르소나를 제안한다.

**완료 기준: 모든 페르소나 행에 `기술수준·인내심` 값이 채워져 있을 때 이 단계가 끝난다.** 값을 정할
근거가 없으면 제품 스펙·권한 모델로 추론해서 채우고 그 사실을 `degraded`에 적는다. 이 값은 Phase 3의
능력 제약(이탈 임계)이 그대로 읽는다.

> 인터페이스별 페르소나 예시: `references/persona-templates.md` 참조

## Phase 3: 시나리오 기반 시뮬레이션

각 페르소나가 **실제 업무 상황에서 하는 행동**을 순서대로 수행한다.

### 페르소나는 한 번에 하나씩, 세션을 끊고 넘어간다

**다음 페르소나로 넘어가기 전에 세션을 끊는다.** UI에 로그아웃이 있으면 그것을 쓰고(페르소나가 실제로
하는 행동이다), 없으면 저장된 인증 상태를 지우고 진입점부터 다시 연다. **끊겼는지 반드시 확인한다** —
진입점이 로그인 화면(또는 비로그인 첫 화면)으로 돌아와야 한다.

안 끊으면 두 가지가 깨진다. 두 번째 페르소나부터 **"첫 사용 30초" 경험이 거짓**이 되는데, 그건
Phase 4 PMF 체크리스트의 첫 항목이다. 그리고 관리자 → 실무자 순서로 돌면 실무자가 볼 수 없어야 할
화면을 보고 지나간다.

**페르소나는 한 번에 하나씩 순차로 돌린다.** 같은 브라우저 컨텍스트에서 동시에 실행하면 서로의
로그인·페이지 상태를 밟는다.

출발점은 각 인터페이스의 **가장 자연스러운 진입점**이다.

### 페르소나 역량으로 행동하기 (능력 제약)

**너는 실제 타깃 유저보다 훨씬 유능하다. 그 능력으로 마찰을 뚫고 지나가면 이 테스트는 무효가
된다** — 실제 유저라면 이탈했을 자리가 "문제없음"으로 기록되기 때문이다. 페르소나의 기술 수준·
인내심에 맞춰 스스로를 제약한다:

- **문구는 한 번 읽은 그대로 받아들인다.** 에러 메시지·라벨·안내가 페르소나 수준에서 바로 이해되지
  않으면 그 자리에서 막힌 것으로 기록한다
- **이탈 임계.** 낮은 인내심(일반 사용자)은 원하는 동작이 **2회 시도** 안에 안 되면 이탈로 간주하고
  Friction/Gap으로 기록한다. 높은 인내심(파워유저·개발자)이라도 3-4회를 넘기지 않는다. "결국
  찾아냈다"는 성공이 아니라 마찰의 증거다
- **탐색 비용을 센다.** 화면/출력에서 다음 액션을 몇 초(1-2회 시선 이동) 안에 못 찾으면 비직관적으로
  판정한다. 여러 메뉴를 뒤져 찾아낸 경로는 "동작함"이 아니라 마찰이다
- **표면만 본다.** UI/CLI/응답이 실제로 드러내는 정보만으로 판단한다 — 코드·내부 문서·콘솔·네트워크
  로그는 페르소나의 눈 밖이고, 제품 스펙은 시나리오 설계용이다
- **성공 여부가 아니라 경험을 기록한다.** 태스크를 완료했더라도 그 과정의 마찰·혼란을 빠짐없이 남긴다

### 인터페이스별 테스트 가이드

**Web UI**: 현재 세션에서 사용할 수 있는 브라우저 자동화 도구로 조작한다. 진입·스냅샷·폼 입력
(로그인 포함)·대기·다이얼로그·스크린샷·콘솔 증거 절차는 **`references/web-tooling.md`를 읽고 그대로 따른다.**

**CLI**: Bash tool로 명령어 실행. 명령어 + 출력을 마크다운 코드블록으로 기록.

**MCP**: MCP tools 직접 호출. 요청/응답을 기록.

**API**: curl 또는 HTTP 클라이언트로 호출. 요청/응답을 기록.

**Plugin**: hook 트리거 관찰. hook 메시지 + 트리거 상황을 기록. **트리거는 새 임시 파일을 만들어
걸고 끝나면 지운다** — 저장소의 기존 파일은 이 스킬의 대상이 아니다. 임시 파일로 트리거되지 않는
hook은 그 사실을 `degraded`에 적고 그 hook을 미검증으로 남긴다.

시뮬레이션 중 무엇을 보고 기록할지는 Phase 4의 **관찰 축**을 기준으로 한다.

**완료 기준: 모든 페르소나가 자기 「오늘의 시나리오」의 마지막 단계에 도달했거나 이탈 임계에 걸려
기록됐을 때 이 Phase가 끝난다.**

### 크로스 인터페이스 (`--cross` 옵션 시)

독립 시나리오 완료 후, 인터페이스 간 데이터 동기화와 일관성을 검증한다:

- 한 인터페이스에서 변경한 내용이 다른 인터페이스에 즉시 반영되는가?
- 동일 데이터의 표현이 인터페이스 간 일관적인가?
- 같은 작업을 다른 인터페이스로 해보면 일관성 문제가 드러난다

## Phase 4: 발견사항 분류

### 분류 체계

- **Bug**: 기능이 스펙과 다르게 동작 (Critical/High/Medium/Low)
- **Friction**: 되긴 되는데 불편하거나 비직관적
- **Gap**: 업무에 필요한데 없는 기능 — PMF 관점에서 치명적인 부재
- **Delight**: 잘 된 부분 — 유지하거나 강화해야 할 것

### 관찰 축

모든 인터페이스에 공통으로 적용한다:

- **마찰 지점**: 원하는 동작을 하는데 예상보다 많은 단계가 필요한 곳
- **혼란 지점**: 다음에 무엇을 해야 할지 모르는 순간
- **실망 지점**: 기대한 기능이 없거나 다르게 동작하는 순간
- **감동 지점**: 예상보다 편리하거나 잘 설계된 부분
- **빈 상태 대응**: 데이터가 없을 때 사용자가 길을 잃지 않는가
- **첫인상**: 처음 보는 화면/출력에서 가장 먼저 눈에 들어오는 것
- **AI slop**: 사람이 만든 제품이 아니라 **모델이 찍어낸 티가 나는 지점**. 페르소나는 이걸
  "성의 없다·믿기 어렵다"로 체감한다

**AI slop 판정 기준과 인터페이스별 추가 관찰은 `references/observation-axes.md`를 읽고 따른다.**

**완료 기준: 각 페르소나 × 각 관찰 축에 대해 기록 또는 「해당 없음」이 남았을 때 이 Phase가 끝난다.**

### 출력 양식

**PMF 체크리스트·발견 표·종합 우선순위 양식은 `references/report-format.md`를 읽고 따른다.**

## Phase 5: 발견을 이슈로 등록

**이 스킬의 산출물은 이슈와 리포트다** — 제품 코드 수정은 build가 한다. 실행 가능한 발견(Bug/Friction/Gap)은
이슈로 등록한다. (Delight는 리포트에만 남긴다 — 문제가 아니다.)

**이슈 관리 방식 로드·기존 이슈 컨벤션 학습·중복 판정·보드 연결·이슈 관리 방식이 없을 때의 폴백은
`skills/project/issue-registration.md`를 읽고 그대로 수행한다.** 아래는 persona-test 고유의 것만이다.

- **동일성 키**는 `화면(인터페이스·라우트) + 문제의 요지`다.
- **출처 마커.** 이슈 본문 맨 위에 `출처: persona-test` 한 줄을 남긴다. 새로 만든 이슈와 기존 이슈에
  접어 넣은 경우 양쪽 모두에 남기고(없으면 한 줄 추가), 접어 넣을 때는 이번에 관측했다는 코멘트를 단다 —
  구현하는 쪽은 그 마커 하나로 "예측이 아니라 관측"을 판정한다.
- **본문 항목.** 출처 줄 다음에 분류(Bug/Friction/Gap), 영향 페르소나, 재현 경로(화면·단계),
  현재 동작 vs 기대 동작, 근거 스크린샷 경로를 남긴다. Bug는 심각도와 **콘솔·네트워크 증거**(있으면)를
  함께 적는다 — 구현자가 재현부터 다시 하지 않아도 되는 것이 이 이슈의 값이다.
- **폴백에서도 리포트·스크린샷은** 상단 **산출물 디렉토리** 절의 규칙대로 보존된다(묻지 않는다).

**루프에서 호출될 때**(`project loop`)는 이슈 관리 방식이 전제조건이므로 항상 이슈로 등록한다. loop은
이 스킬을 **fresh subagent로 dispatch**하므로(=이 세션이 그 subagent다), 서비스 기동·브라우저 구동·발견·
이슈 등록을 자기 컨텍스트에서 직접 수행한 뒤 끝에 아래를 반환한다:

- `persona_ran=true` + 만든 이슈 전체(번호·제목·분류) + **그중 빌드가능 번호 목록** + 동일성 키로 중복
  제거해 안 만든 항목 + **그중 접어 넣은 기존 이슈의 번호**(거르지 않고 그대로). loop은 이 번호들로 `Np`를 세어 수렴을 판정한다.
- 서비스를 기동하지 못해 테스트를 못 했으면 `persona_ran=false` + 기동 실패 사유를 반환한다.
  이것은 "미검사"이며 loop이 그 라운드를 미검증으로 처리한다.
- 묻지 못해 강등한 것이 있으면 `degraded`에 무엇을 어떻게 강등했는지 적는다. **강등이 테스트 범위를
  줄였으면**(대표적으로 테스트 계정 없이 비로그인 범위만 돈 경우) `persona_ran=true`라도
  **`coverage=partial`을 함께 반환한다** — loop은 이것을 `persona_ran=false`와 똑같이 **미검증**으로
  처리한다. 범위가 준 것을 "발견 0"으로 올리면 수렴이 아니라 사각지대다.
- 강등 경로가 이 문서에 적혀 있지 않은 질문에 닿으면 `blocked` + 그 질문을 반환한다.
