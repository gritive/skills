# Persona-Based Service Testing

고객 페르소나를 정의하고 실제 서비스를 **고객처럼 사용**하여 사용성, PMF(Product-Market Fit), 업무 워크플로우 적합성을 검증하는 스킬.

**핵심 원칙**: 이 스킬은 E2E 테스트가 아니다. "기능이 동작하는가?"가 아니라 **"이 서비스로 실제 업무를 할 수 있는가?"**를 검증한다.

## 산출물 규칙

**테스트 산출물(스크린샷·로그·리포트)을 대상 프로젝트에 남기지 않는다.** 산출물은 세션 임시
디렉토리에 두고 리포트는 대화로 출력한다. 프로젝트에 파일로 남기는 것은 사용자가 명시적으로
요청할 때, 사용자가 지정한 경로에만 한다 (Phase 5).

여기서 '산출물'은 **테스트가 만들어내는 부산물**(스크린샷·로그·리포트)을 말한다. 이 스킬은 코드를
직접 고치지 않는다 — 발견은 이슈로 등록한다(Phase 5). **이슈 등록은 이 스킬의 결과물이지 부산물이
아니므로** 이 규칙의 대상이 아니다.

### 임시 디렉토리

`mktemp -d`로 **한 번만** 만들고, 출력된 절대 경로를 기록해 세션 내내 재사용한다 (Bash 호출 간
셸 변수는 유지되지 않는다). 경로를 잃었으면 `mktemp -d`를 다시 부르지 말고
`$TMPDIR/persona-test-{YYYYMMDD}`를 쓴다 — 산출물이 여러 디렉토리로 흩어지지 않게.

### 브라우저 도구와 스크린샷

**Web UI는 Playwright MCP(`mcp__playwright__*`)로 조작한다.** Playwright는 **자체 격리 브라우저**를
띄우므로 사용자의 기존 Chrome 세션·탭과 무관하다 — `browser_navigate`로 대상 URL을 바로 연다.
**여러 탭을 쓰지 않는다.** 한 페이지에서 이동하며 시나리오를 진행한다.

**조작은 스냅샷 기반으로 한다.** `browser_snapshot`으로 접근성 트리(각 요소의 `ref` 포함)를 얻고,
그 `ref`로 `browser_click`·`browser_type`·`browser_select_option`을 호출한다. 좌표 클릭이 아니라
요소 참조로 조작하므로 페르소나가 실제로 상호작용하는 요소를 정확히 겨냥한다. 동적 로딩·전환은
`browser_wait_for`로 기다린다.

**주요 화면은 스크린샷으로 남겨 보존한다 — 나중에 쓸 수 있게.** 스크린샷은 근거 보존용인 동시에
**시각적 UX 평가의 판정 근거**다 (Phase 4의 Web UI 관찰 포인트 참조). 스냅샷(DOM)만 읽지 말고
페르소나가 실제로 보는 렌더된 화면을 본다. 빈 상태·에러 화면·완료 화면, 페르소나 시나리오의 각
핵심 단계 등 발견사항의 근거가 될 화면은 반드시 찍는다:

- `browser_take_screenshot`에 `filename`을 주어 저장한다. 저장 경로가 **tool 결과로 돌아온다**
  (Playwright MCP가 관리하는 출력 디렉토리이며 프로젝트 cwd가 아니다)
- 실행 중에는 반환 경로를 세션 임시 디렉토리에 모아 두고(`cp`/`mv`) 리포트에서 참조한다. 파일명은
  `{페르소나ID}-{단계}.png`처럼 **나중에 찾기 쉽게** 붙인다
- **세션 임시 디렉토리는 사라질 수 있으므로, 보존용 저장 위치를 사용자에게 확인해 그곳에 복사한다.**
  산출물 규칙상 대상 저장소에 스킬 이름 디렉토리를 만들지 않으니 경로는 **사용자 지정 위치**를 쓴다
  (경로를 못 받았으면 물어본다). **묻지 못하는 실행이면 보존하지 않는다** — 임시 디렉토리에 두고
  리포트에서 참조만 하며, 보존을 못 했다고 `degraded`에 적는다. 임의의 경로를 골라 저장하지 않는다
- 리포트의 각 발견사항에 근거 스크린샷을 연결하고, 핵심 화면은 `SendUserFile`로 사용자에게 전달한다

리포트·로그를 파일로 남길 일이 생겨도 위 임시 디렉토리에 둔다.

### 예외 — hook 트리거를 위한 편집

`plugin` 인터페이스는 hook을 띄우려면 대상 프로젝트 파일을 건드려야 한다. 이건 산출물이 아니라
테스트 조작이다. 다음 순서로 한다:

1. 가능하면 **새 임시 파일**을 만들어 트리거하고 테스트 후 지운다. 기존 파일을 건드리지 않는 게
   가장 안전하다
2. 기존 파일을 고쳐야만 하면, 먼저 **`cp`로 임시 디렉토리에 원본을 백업한다.** git 저장소면
   `git status`로 **그 파일에 커밋되지 않은 변경이 있는지 본다. 있으면 건드리지 않는다** — 원복이
   사용자 작업을 날린다
3. 테스트 후 **백업본을 `cp`로 되돌려** 원복한다. 2단계에서 그 파일이 clean임을 확인했으므로 파일
   하나를 지정한 `git checkout -- <파일>`도 안전하다
4. 도중에 중단되면 남아있는 편집을 사용자에게 알린다

**원본을 `Read`해서 기억했다가 `Write`로 되쓰는 방식으로 원복하지 않는다.** `Read`는 줄번호를
붙이고 긴 파일을 잘라서 보여주므로, 그 내용을 되쓰면 **사용자 파일이 잘린 채 덮어써진다.** 원복은
바이트 단위 복사(`cp`)나 `git checkout -- <파일>`로만 한다.

**전역 복원 명령을 쓰지 않는다.** `git checkout -- .`, `git restore .`, `git stash`는 이 스킬이
건드리지 않은 사용자의 작업까지 날린다. 원복 대상은 **내가 고친 파일뿐이다.** `git status`에
무관한 변경이 보여도 그건 사용자 것이니 손대지 않는다.

## Phase 1: 준비

### 1-1. 테스트 대상 인터페이스 선택

사용자에게 테스트할 인터페이스를 확인한다. 복수 선택 가능.

**묻지 못하는 실행이면**(subagent에는 `AskUserQuestion`이 없다 — 예: `project loop`이 dispatch한 경우)
멈추지 말고 **감지된 인터페이스 전부**를 대상으로 하고, 그렇게 강등했다고 `degraded`에 적어 반환한다.
감지된 것이 하나도 없으면 그때는 `blocked`로 반환한다 — 테스트할 대상이 없는 것이지 강등이 아니다.

| 인터페이스 | 설명                   | 도구                 |
| ---------- | ---------------------- | -------------------- |
| `web`      | 브라우저 기반 웹 UI    | Playwright MCP       |
| `cli`      | CLI 명령어             | Bash tool            |
| `mcp`      | MCP 도구 직접 호출     | MCP tools            |
| `api`      | REST/GraphQL API       | Bash (curl)          |
| `plugin`   | hook/plugin 워크플로우 | Edit + Bash          |

- 복수 선택 시 각 인터페이스를 **독립적으로** 테스트
- `--cross` 옵션 추가 시 인터페이스 간 **크로스 시나리오**도 실행

### 1-2. 프로젝트 설정 로딩

**CLAUDE.md에서 `Persona Test` 섹션을 찾아** 프로젝트별 설정을 로딩한다.

찾아야 할 정보:

- **인터페이스 URL/명령어**: 각 인터페이스의 접속 주소 또는 실행 명령
- **테스트 계정**: 계정 정보 파일 위치 (예: `docs/test-accounts.md`)
- **제품 스펙**: 제품이 해결하는 문제와 핵심 가치 문서
- **프로젝트 페르소나**: 미리 정의된 페르소나 (있으면 사용, 없으면 Phase 2에서 생성)

CLAUDE.md에 설정이 없으면 사용자에게 직접 확인:

1. 서비스에 어떤 인터페이스가 있는가?
2. 테스트 계정은 어디에 있는가?
3. 주요 사용자 역할은 무엇인가?

**묻지 못하는 실행이면**(subagent에는 `AskUserQuestion`이 없다) 항목마다 갈린다:

| 못 받은 것 | 처리 |
| --- | --- |
| 인터페이스 URL/명령어 | 저장소에서 찾는다(README 실행 절, `package.json` scripts, compose 파일). 못 찾으면 **테스트할 대상이 없으므로 `blocked`** |
| 주요 사용자 역할 | 제품 스펙·코드의 권한 모델에서 추정하고 `degraded`에 근거를 적는다 |
| **테스트 계정** | **강등하지 않는다.** 인증이 필요한 서비스에서 계정 없이 도는 것은 강등이 아니라 **다른 테스트**다 — 로그인 화면만 보고 "Friction 발견"을 만들어 낸다. 인증 없이 닿는 범위가 없으면 `blocked`, 있으면 **비로그인 범위만 테스트했다고 `degraded`에 명시**하고 그 라운드를 미검증으로 올린다 |

계정을 못 받은 채 도는 것을 정상 통과로 보고하지 마라 — 그것이 이 표의 이유다.

> 프로젝트 관리자를 위한 CLAUDE.md 설정 가이드: `references/claude-md-setup.md` 참조

## Phase 2: 페르소나 정의

### 좋은 페르소나의 조건

- 서비스의 **다른 측면**을 사용하는 역할 (예: 관리자 vs 실무자)
- **구체적인 업무 목표**를 갖고 있음 (예: "오늘 해야 할 3개 작업을 파악하고 하나를 완료 처리")
- 각 페르소나마다 고유한 **pain point 가설**이 있음
- "오늘의 시나리오"는 5-10분 분량의 현실적 업무 흐름
- **기술 수준과 인내심을 명시한다** (예: `비기술·낮음`, `개발자·높음`). 이 값이 Phase 3의
  능력 제약(아래 "페르소나 역량으로 행동하기")을 결정한다 — 없으면 시뮬레이션이 페르소나가
  아니라 유능한 모델의 경험이 되어버린다

### 페르소나 템플릿

| ID  | 이름 | 역할 | 기술수준·인내심 | 업무 목표 | 오늘의 시나리오 | 핵심 검증 |
| --- | ---- | ---- | --------------- | --------- | --------------- | --------- |

CLAUDE.md에 프로젝트 페르소나가 정의되어 있으면 사용한다. 없으면 제품 스펙과 사용자 입력을 기반으로 3-5개 페르소나를 제안한다. **묻지 못하는 실행이면 제품 스펙과 코드의 권한 모델만으로 3-5개를 직접 정하고**(제안하고 기다리지 않는다) 그 사실을 `degraded`에 적는다.

> 인터페이스별 페르소나 예시: `references/persona-templates.md` 참조

## Phase 3: 시나리오 기반 시뮬레이션

각 페르소나가 **실제 업무 상황에서 하는 행동**을 순서대로 수행한다.

### 시나리오 설계 원칙

- 출발점은 해당 인터페이스의 **가장 자연스러운 진입점**
- "기능이 동작하는가?"가 아니라 **"이 사람이 이 도구로 자기 업무를 자연스럽게 해결할 수 있는가?"**
- 각 시나리오는 **5-10분 분량**의 현실적 업무 흐름

### 페르소나 역량으로 행동하기 (능력 제약)

**너는 실제 타깃 유저보다 훨씬 유능하다. 그 능력으로 마찰을 뚫고 지나가면 이 테스트는 무효가
된다** — 실제 유저라면 이탈했을 자리가 "문제없음"으로 기록되기 때문이다. 페르소나의 기술 수준·
인내심에 맞춰 스스로를 제약한다:

- **불친절한 문구를 '해독'하지 않는다.** 에러 메시지·라벨·안내가 페르소나 수준에서 바로 이해되지
  않으면 그 자리에서 막힌 것으로 기록한다. 숨은 의미를 추론해 넘어가지 않는다
- **이탈 임계.** 낮은 인내심(일반 사용자)은 원하는 동작이 **2회 시도** 안에 안 되면 이탈로 간주하고
  Friction/Gap으로 기록한다. 높은 인내심(파워유저·개발자)이라도 3-4회를 넘기지 않는다. "결국
  찾아냈다"는 성공이 아니라 마찰의 증거다
- **탐색 비용을 센다.** 화면/출력에서 다음 액션을 몇 초(1-2회 시선 이동) 안에 못 찾으면 비직관적으로
  판정한다. 여러 메뉴를 뒤져 찾아낸 경로는 "동작함"이 아니라 마찰이다
- **커닝하지 않는다.** 페르소나는 코드·내부 문서를 못 본다. UI/CLI/응답이 실제로 드러내는 정보만으로
  판단한다 (제품 스펙은 시나리오 설계용이지 시뮬레이션 중 참조용이 아니다)
- **성공 여부가 아니라 경험을 기록한다.** 태스크를 완료했더라도 그 과정의 마찰·혼란을 빠짐없이 남긴다

### 인터페이스별 테스트 가이드

**Web UI**: Playwright MCP로 브라우저 조작 (`browser_navigate`로 진입 → `browser_snapshot`으로
요소 파악 → `browser_click`/`browser_type`으로 조작, `browser_wait_for`로 대기). 로컬 개발 서버라
로그인이 필요하면 1-2에서 로딩한 테스트 계정으로 `browser_type`을 써서 로그인 폼을 직접 채운다.
탭은 쓰지 않는다. 스크린샷 처리는 상단 **산출물 규칙**을 따른다.

**CLI**: Bash tool로 명령어 실행. 명령어 + 출력을 마크다운 코드블록으로 기록.

**MCP**: MCP tools 직접 호출. 요청/응답을 기록.

**API**: curl 또는 HTTP 클라이언트로 호출. 요청/응답을 기록.

**Plugin**: Edit + Bash로 hook 트리거 관찰. hook 메시지 + 트리거 상황을 기록. 트리거용 편집은
상단 **산출물 규칙 → 예외**의 절차를 따른다 (새 파일 우선, 원복, `git status` 확인).

### 시뮬레이션 중 관찰 포인트

- **마찰 지점**: 원하는 동작을 하는데 예상보다 많은 단계가 필요한 곳
- **혼란 지점**: 다음에 무엇을 해야 할지 모르는 순간
- **실망 지점**: 기대한 기능이 없거나 다르게 동작하는 순간
- **감동 지점**: 예상보다 편리하거나 잘 설계된 부분
- **빈 상태 대응**: 데이터가 없을 때 사용자가 길을 잃지 않는가
- **정보 계층**: 중요한 정보가 눈에 잘 띄는가

### 크로스 인터페이스 (`--cross` 옵션 시)

독립 시나리오 완료 후, 인터페이스 간 데이터 동기화와 일관성을 검증한다:

- 한 인터페이스에서 변경한 내용이 다른 인터페이스에 즉시 반영되는가?
- 동일 데이터의 표현이 인터페이스 간 일관적인가?

## Phase 4: 발견사항 분류

### 분류 체계

- **Bug**: 기능이 스펙과 다르게 동작 (Critical/High/Medium/Low)
- **Friction**: 되긴 되는데 불편하거나 비직관적
- **Gap**: 업무에 필요한데 없는 기능 — PMF 관점에서 치명적인 부재
- **Delight**: 잘 된 부분 — 유지하거나 강화해야 할 것

### 인터페이스별 관찰 포인트

**Web UI**: 클릭/단계 수, 반응 속도, 빈 상태 UI, 에러 상태 UI, 단축키, 접근성. **시각적 평가는
스크린샷을 근거로 한다** — 화면을 5초 보고 (1) 시선이 가장 먼저 가는 곳이 페르소나 목표와 일치하는가,
(2) 시각적 계층상 중요 정보가 눈에 띄는가, (3) 가독성·정보 밀도가 페르소나 기술 수준에 맞는가를 판정

**CLI**: 에러 메시지→다음 행동 안내 품질, 출력 가독성, `--output json/table` 전환, 파이프 친화성, help 품질, 명령어 직관성

**MCP**: AI 에이전트가 응답만으로 다음 행동 결정 가능성, 에러 응답 구조화, 빈 상태 응답 유용성, 토큰 효율성

**API**: 응답 구조 일관성, 에러 코드/메시지 품질, 페이지네이션, 버전 관리

**Plugin**: hook 방해도, 메시지 명확성, 등록 후 투명한 동작

## Phase 5: 발견을 이슈로 등록 (코드를 직접 고치지 않는다)

**이 스킬은 발견한 문제를 직접 고치지 않는다.** 실행 가능한 발견(Bug/Friction/Gap)은 이 프로젝트의
**이슈 관리 방식**에 따라 이슈로 등록한다. 이슈 생성 패턴은 `project`의 `prd-to-issue`와 동일하다.
(Delight는 문제가 아니므로 이슈로 만들지 않는다 — 리포트에만 남긴다.)

먼저 이 프로젝트에 이슈 관리 방식이 있는지 확인한다:

- 대상 `CLAUDE.md`의 "이슈 관리" 섹션을 읽어 org/보드/마일스톤·연결 방식·라벨 컨벤션을 파악한다.
  **org/보드 번호를 이 문서에 하드코딩하지 않는다** — 항상 대상 CLAUDE.md에서 읽는다.
- "이슈 관리" 섹션이 없거나 `gh`가 인증돼 있지 않으면 **이슈 관리 방식이 없는 것으로 보고 아래
  "이슈 관리 방식이 없을 때"로 간다.**

이슈 관리 방식이 있으면:

1. **기존 이슈 컨벤션·중복 확인** — `gh issue list --state all`로 이미 있는 이슈를 보고, 대표 이슈
   2~3개 본문(`gh issue view <n>`)으로 제목 접두 분류·본문 섹션 구조·보드 연결 컨벤션을 답습한다.
   추측하지 않는다.
2. **동일성 키로 중복을 거른다.** 발견의 동일성은 **`화면(인터페이스·라우트) + 문제의 요지`**로
   판정한다 — **심각도와 재현 라인은 키에서 뺀다**(코드가 바뀌면 흔들린다). 같은 키의 발견을 이미
   다루는 이슈가 열려 있으면 **새로 만들지 않는다. 대신 그 이슈 본문에 `출처: persona-test`가 없으면
   추가하고(위치는 어디든 되지만 한 줄로 독립시킨다), 이번에 관측했다는 코멘트를 단다.**
   **접어 넣은 기존 이슈가 아직 열려 있으면 그 번호도 호출자에게 올린다** — 접었다고 해결된 게 아니라
   아직 처리 대기라는 뜻이고, 호출자는 이것으로 수렴을 판정한다. 거르지 말고 그대로 올린다. 이슈를 새로 만들 때만 마커를 남기면, 이미
   추적 중이던 이슈로 접힌 발견은 "실제로 돌려 보니 드러났다"는 사실을 영영 못 갖는다 — 구현하는 쪽은
   그 마커 하나로 판정하므로, 없으면 관측된 파손이 평범한 이슈로 취급된다.
   **단 `demo-debt` 라벨 이슈는 이 대조의 대상이 아니다.** 그건 "나중에 하겠다고 미뤄 둔 것"이지
   이 발견을 다루는 이슈가 아니고, 네가 방금 **실제로 돌려 보니 드러났다**는 것은 미룰 수 없다는
   뜻이다. 같은 키가 `demo-debt`에만 있으면 **새 이슈를 만든다**(호출자가 `--demo` 맥락과 그 목록을
   넘겼으면 어느 항목에 대응하는지 반환에 짝지어 올린다).
3. **새 발견을 각각 이슈로 만든다.** 본문에 **`출처: persona-test` 한 줄을 먼저 적고**, 이어서
   분류(Bug/Friction/Gap), 영향 페르소나, 재현 경로(화면·단계), 현재 동작 vs 기대 동작, 근거 스크린샷
   경로를 남긴다. Bug는 심각도를 함께 적는다.
   **`출처` 줄을 빠뜨리면 안 된다.** 이 이슈를 나중에 구현하는 쪽은 그 줄 하나로 "이건 예측이 아니라
   관측이다"를 판정한다 — 없으면 관측된 파손이 평범한 이슈로 취급돼 다시 미뤄질 수 있다.
4. 각 이슈 생성 직후 1단계에서 확인한 규칙대로 보드에 연결한다.

### 이슈 관리 방식이 없을 때 (폴백)

- 이슈를 만들지 말고 Phase 4의 표를 **대화로** 리포트한다.
- 리포트·스크린샷을 파일로 남길지는 사용자에게 먼저 확인한다 — 경로를 받지 못했으면 물어보고, 확인
  없이 대상 저장소에 파일을 만들지 않는다(상단 산출물 규칙). **묻지 못하는 실행이면 파일을 만들지
  않는다** — 그것이 "확인 없이 만들지 않는다"의 기본값이다. 리포트는 반환 텍스트로 돌려주고
  `degraded`에 적는다.

**루프에서 호출될 때**(`project loop`)는 이슈 관리 방식이 전제조건이므로 항상 이슈로 등록한다. loop은
이 스킬을 **fresh subagent로 dispatch**하므로(=이 세션이 그 subagent다), 서비스 기동·브라우저 구동·발견·
이슈 등록을 자기 컨텍스트에서 직접 수행한 뒤 끝에 아래를 반환한다:

- `persona_ran=true` + 만든 이슈 전체(번호·제목·분류) + **그중 빌드가능 번호 목록** + 동일성 키로 중복
  제거해 안 만든 항목 + **그중 접어 넣은 기존 이슈가 아직 열려 있는 것의 번호**(2단계 참조 — 거르지 않고
  그대로). loop은 이 번호들로 `Np`를 세어 수렴을 판정한다.
- 서비스를 기동하지 못해 테스트를 못 했으면 `persona_ran=false` + 기동 실패 사유를 반환한다. 발견 0을
  "깨끗함"으로 보고하지 않는다 — 검사하지 못한 것이다(loop이 그 라운드를 미검증으로 처리한다).
- 묻지 못해 강등한 것이 있으면 `degraded`에 무엇을 어떻게 강등했는지 적는다. **강등이 테스트 범위를
  줄였으면**(대표적으로 테스트 계정 없이 비로그인 범위만 돈 경우) `persona_ran=true`라도
  **`coverage=partial`을 함께 반환한다** — loop은 이것을 `persona_ran=false`와 똑같이 **미검증**으로
  처리한다. 범위가 준 것을 "발견 0"으로 올리면 수렴이 아니라 사각지대다.
- 강등 경로가 이 문서에 적혀 있지 않은 질문에 닿으면 `blocked` + 그 질문을 반환한다. 지어내지 않는다.

## Tips

- **고객처럼 생각하기**: "이 버튼이 동작하나?"가 아니라 "내가 이 역할이라면 뭘 하고 싶을까?"
- **비교 관점**: 같은 작업을 다른 인터페이스로 해보면 일관성 문제 발견
- **첫인상 기록**: 처음 보는 출력/화면에서 가장 먼저 눈에 들어오는 것 기록
- **5초 테스트**: 출력을 5초 보고 "오늘 내가 해야 할 일이 뭔지 알 수 있는가?"
- **문제 중심 기록**: 문제 발견 시에만 상세 기록 (문제 없으면 스킵)
