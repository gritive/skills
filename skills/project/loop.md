# project loop

에픽마다 `build → gap → design-review → persona-test`로 점검하고, 라운드 끝에서 같은 넷을 전역으로 한 번 더
돌려 새 빌드가능 이슈가 없을 때까지 반복한다.

위임 계약:

- `build`는 현재 세션에서 호출한다.
- `gap`·`design-review`·`persona-test`는 각각 fresh subagent에서 실행한다.
- subagent는 요구된 반환 계약을 지켜야 하며 계약 누락은 중단이다.

## 입력

- 대상은 **현재 작업 디렉터리**로 고정한다.
- 대상 이슈 — 선택 인자(`/project loop #10`). `/project #10`은 같은 명령이다. 지정하면 **이슈 범위 모드**로
  실행해 #10과 명시적으로 연결된 기존·파생 이슈를 모두 해결하고 멈춘다. 관계 없는 프로젝트 이슈는 선택하지 않는다.
- 라운드 수 상한 — 선택 인자(`/project loop 2`). 없으면 기본 **10**. 이 값은 정상 종료점이 아니라
  **무한 루프 방지 backstop**이다 — 루프는 보통 그 전에 수렴으로 끝난다. 라운드마다 백로그 전체를
  소진하므로 무겁다는 점만 유의한다.
- `--skip-review` — 선택 플래그. 모든 내부 `build` 호출에 그대로 전달한다. 효과는 `build.md` 9.5단계가
  정의한다. 예: `/project loop --skip-review`.
- 선정 순서는 이슈의 우선순위를 따른다(`build.md` 2단계). 이슈 범위 모드에서는 관련 이슈 처리 집합 안에서만 이 순서를 적용한다.

### 이슈 범위 모드 (`#N`)

시작 전에 `gh api repos/{owner}/{repo}/issues/N`으로 열린 이슈인지 확인한다. 없거나 닫혔으면 보고하고 멈춘다. 그런 다음
`references/issue-scope.md`를 읽고 seed #N의 scope를 계산한다. 모든 build·gap·design·persona에 scope와
관계 근거를 전달하고 각 Phase 뒤 폐쇄를 다시 계산한다. 관계 밖 이슈는 선택하거나 검사하지 않는다.

라운드 상한을 함께 주면 이슈 범위 모드 loop에 적용한다(예: `/project loop #10 3`). 없으면 기본 10이다. 상한은
backstop이며, `issue-scope.md`의 scope 수렴이 정상 종료점이다.

## 전제조건 — 없으면 시작하지 않는다

- **이슈 관리 방식**(gh 인증 + 대상 `CLAUDE.md`의 "이슈 관리" 섹션)이 있어야 한다. 없으면 gap/persona가
  이슈를 못 만들고 build가 소비할 백로그가 없다 — "이슈 관리 방식이 필요하다"고 알리고 멈춘다.
- `build`·`gap`·`persona-test`가 있어야 한다 — 이 셋은 전제다(`design-review`는 없어도 루프가 돈다,
  Phase B'). `codebase-review` 리뷰어 지침 문서는 기본
  경로에서 필요하고 `--skip-review`이면 불필요하다. **판정은 `build.md` 0단계가 한다** — loop은 전제로만 적는다.
- **persona 단계는 실행 가능한 서비스 + 브라우저를 요구한다.** 없어도 루프는 돈다(아래 Phase C 참조) —
  다만 그 라운드 persona는 "미검증"이 되어 수렴 종료 신호로 쓰이지 못한다.
- **`design-review`(gstack)는 우리 플러그인 스킬이 아니므로 없는 환경이 있다.** 실행 조건과 없을 때의
  처리는 Phase B'가 정한다.

## 핵심 개념 — 실행 큐는 "새 빌드가능 이슈"다

전역 모드의 모든 판정(완료·정체·반복)은 gap/persona의 **원시 발견 수**가 아니라 **새로 만든 빌드가능
이슈 수**로 잰다. 이슈 범위 모드는 이 절의 공식을 쓰지 않고 `issue-scope.md`의 scope 큐를 쓴다.

```
실행 큐(라운드) = gap(Ng) + design-review(Nd) + persona(Np)
                + persona가 기존 열린 이슈로 접은 관측(그 번호가 직전 라운드에 안 세어졌을 때만)
                − (이미 있는 중복) − (빌드 제외 클래스)
```

**직전 라운드에 이미 센 번호를 빼는 이유:** 두 라운드 연속 build가 안 태웠다는 것은 열거된 제외 클래스
밖의 사유(신뢰 경계 위반, 하드 게이트, 프로젝트 고유 보류 접두어)로 build가 건너뛰고 있다는 뜻이고,
계속 세면 큐가 영영 0이 되지 않아 라운드 상한까지 돌고 "정체"로 끝난다.

**`Ng`/`Nd`/`Np`는 각 Phase가 돌려주는 "빌드가능 이슈 번호 목록"의 약칭이다** — 셋은 같은 것이고
Phase만 다르다. 판정은 항상 **셋의 합**으로 한다.

**판정 단위는 새 빌드가능 이슈 수 하나다.** gap/persona는 라운드 간 기억이 없어 이미 이슈로 있는 gap과
build가 손대지 않기로 한 항목을 매 라운드 다시 발견하므로, 원시 발견 수로는 큐가 0이 되지 않는다.

### 빌드 제외 클래스

build가 **어느 경우에도 구현하지 않는** 이슈는 큐에서 뺀다. 클래스 목록과 식별 방법은 `build.md`
2단계의 "항상 제외하는 클래스" 표를 그대로 쓴다 — loop은 세지 않을 뿐 정의를 따로 두지 않는다.

**에픽은 제외 클래스가 아니다.** build가 준비된 하위 이슈를 구현하고, uncovered 범위를 split·구현하며,
완료된 에픽을 닫는다. 다른 빌드가능 이슈를 소진한 뒤 미완료 에픽 자체나 그 leaf가 제외 클래스에만
걸려 있으면 build가 `stopped`를 반환하므로 loop도 즉시 멈춘다. 열린 에픽을 큐에서 빼서 수렴을
만들지 않는다.

즉 한 라운드의 gap·design·persona가 `question`·`credential` 이슈만 만들었고 그것이 미완료 에픽
자체나 leaf가 아니라면 **빌드가능 0 → 수렴**이다. 에픽과 연결됐으면 build가 `stopped`로 올리므로
사람·고객이 해제해야 할 미완료 제품 범위로 보고한다.

## 라운드 구조

한 라운드는 순차 드레인이다:

```
라운드 시작
 ├─ A. 에픽마다: build #<에픽 root> → 에픽 게이트(gap → design → persona, 같은 scope)
 ├─ A'. build (drain)                 에픽에 안 걸린 단독 이슈 소진
 ├─ B. gap → 새 빌드가능 이슈
 ├─    build (drain)                  gap이 만든 이슈 소진
 ├─ B'. design-review → 새 빌드가능 이슈   (UI 변경이 있었던 라운드만)
 ├─    build (drain)                  design이 만든 이슈 소진
 ├─ C. persona → 새 빌드가능 이슈       (서비스 기동 가능할 때만)
 ├─    build (drain)                  persona가 만든 이슈 소진
 └─ D. 이번 라운드의 새 빌드가능 이슈 == 0  AND  persona가 실제로 돌았음 → 수렴·종료
       아니면 다음 라운드
```

라운드 시작 시 한 줄로 보고한다: `라운드 k/상한 시작`.

### 보드 조회 예산

각 내부 build는 열린 이슈 목록만 fresh fetch하고, 우선순위상 검토하는 후보·상위 에픽만 단건으로 재검증한다(`build.md` 1단계). 어느 Phase에서도 `gh project item-list --limit 1000`를 호출하지 않는다. 새로 연결하거나 Status를 바꾼 항목도 단건 확인한다.

### 모든 Phase에서 build를 호출하는 법 — 결과를 반드시 구분한다

**`Skill` 툴로 `gritive:project`의 `build`를 호출하고 그 지침을 그대로 수행한다**(= `build.md`).
이슈 범위 모드에서는 `issue-scope.md`의 scope를 내부 build 입력과 각 reviewer dispatch에 전달한다.
위임하지 않는 이유는 이 문서 앞머리 참조.

**build에 넘기는 인자는 scope 하나뿐이다.** Phase A는 에픽 root 번호를 scope로 주고, A'·B·B'·C는 인자
없이 호출해 남은 백로그를 끝까지 드레인한다. 이슈 수 상한을 주면 백로그가 부분만 소진돼 "빌드가능 이슈
0" 판정이 거짓이 되고 큐 회계가 깨진다. (`/project build N`의 N은 loop의 라운드 상한과 다른 값이다.)

**`--skip-review`는 모든 build 호출에 똑같이 전달한다**(라운드 상한 정수는 loop 내부에만 둔다). 한 호출이라도
플래그가 다르면 build가 소비한 범위와 큐가 잰 범위가 어긋난다.

판정은 `build.md`의 outcome 계약만 따른다. build가 끝나면 완료 보고의 `outcome`을 읽는다. 이 구분이 이 루프의 최악의 실패("검사 안 함"을 "완료"로
오인)를 막는다. **보고에서 아래 셋 중 하나로 확정될 때만 판정한다** — 확정할 수 없으면 멈춘다.

| `outcome` | 루프의 처리 |
| --- | --- |
| `drained` | **다음 Phase로** |
| `excluded_only` | 전역 모드는 **다음 Phase로**. 이슈 범위 모드는 관련 제외 이슈의 번호·사유와 함께 `stopped`로 끝낸다 |
| `stopped` | **루프 전체를 멈춘다.** gap/persona로 넘어가지 않고, 수렴 선언도 하지 않는다. build가 넘긴 중단 사유를 그대로 전하고 사용자 지시를 기다린다 |

**판정은 `outcome` 한 줄로만 한다.** build는 못 고친 리뷰 발견과 범위 밖 발견을 완료 보고에 그대로
싣고 정상 진행하므로, 보고 본문의 발견 유무는 판정 근거가 아니다. `stopped`면 루프도 멈춘다.

**부분 구현은 build 안에서 처리된다** — `build.md` 3.5단계가 같은 이슈를 재개시키거나 `build-blocked`를
붙인다. "완료 조건이 남았다"는 반환이 오면 `outcome`이 규약을 벗어난 것이므로 위 규칙대로 멈춘다.

### Phase A — 에픽 단위 drain·게이트

**백로그가 크면 전역 drain을 기다리는 동안 gap·design·persona가 한 번도 안 돈다.** 에픽 하나가 끝날
때마다 그 범위만 점검해 피드백을 앞당긴다.

1. 1단계 후보 중 **에픽 root**를 우선순위 순으로 하나 고른다. 남은 에픽이 없으면 Phase A'로 간다.
2. 그 root 번호를 scope로 `build`를 호출한다(위 build 호출 규칙). scope 계산·불변식은
   `references/issue-scope.md`가 정한다.
3. `outcome`이 `drained`·`excluded_only`면 **에픽 게이트**를 돈다 — gap → design-review → persona를
   같은 에픽 scope로, 아래 Phase B·B'·C 절이 정한 방식 그대로 dispatch한다. `stopped`면 루프를 멈춘다.
4. 다음 에픽으로 돌아간다.

**에픽 게이트의 발견은 그 에픽의 형제 이슈로 만든다** — 방금 종결한 에픽의 하위로 붙이면 에픽이 다시
열려 영영 닫히지 않는다. 원 에픽 번호를 관계 근거로 남긴다.

**게이트 발견은 그 에픽에서 다시 소진하지 않는다.** 이번 라운드 실행 큐에만 더하고 다음 에픽으로
넘어간다 — 같은 에픽에서 build↔게이트를 반복하면 라운드가 한 에픽에 갇힌다. 만들어진 이슈는 A'와 다음
라운드의 평범한 대상이다.

**persona는 그 에픽이 사용자 도달 가능한 흐름을 끝냈을 때만 돈다.** 내부 리팩터·인프라 에픽은 건너뛰고
사유를 한 줄로 보고한다. dispatch 프롬프트에 **"열린 백로그 이슈는 기지(旣知) 미구현이다 — 새 결함이
아니라 그 이슈로 접는다"**를 명시한다. 아직 백로그가 남은 시점이라 이 문장이 없으면 미구현 화면이 새
결함으로 올라와 큐가 부풀고 정체 감지가 오탐으로 터진다.

**에픽 게이트는 수렴을 선언하지 않는다.** 수렴 증명은 전역 Phase B·B'·C가 한다.

### Phase A' — 단독 이슈 drain

에픽에 걸리지 않은 나머지 빌드가능 이슈를 인자 없는 `build` 한 번으로 소진한다. `outcome` 처리는 위
표와 같다.

### Phase B·C 위임 계약

각 작업은 fresh subagent 하나에 맡기고 다음 공통 정보를 전달한다.

- 대상 저장소 경로와 적용되는 `AGENTS.md`·`CLAUDE.md`
- 현재 라운드 번호와 이전 Phase 결과
- 실행할 스킬 파일과 원문 반환 계약
- 이슈 범위 모드면 `references/issue-scope.md` 원문, 현재 scope 번호·관계 근거, 이 Phase의 scope 검사 범위
- 파일 탐색·편집 도구 규칙

공통 반환 envelope는 gap과 persona에만 적용한다:

| 필드 | 내용 |
| --- | --- |
| `status` | `ok`, `degraded`, `blocked`, `failed` |
| `created_issues` | 새 이슈 번호·제목·유형 |
| `buildable_issues` | 그중 build 제외 클래스가 아닌 이슈 번호 |
| `scope_additions` | 이슈 범위 모드에서 `issue-scope.md`가 정한 새 편입 이슈·관계 근거; 전역 모드는 `N/A` |
| `persona_ran` | persona 실행 여부; gap은 `N/A` |
| `coverage` | 검사한 문서·화면·흐름 |
| `blocked` | 막힌 항목과 근거 |
| `degraded` | 강등 내역 |

subagent가 `blocked`·`failed` 또는 계약 누락을 반환하면 루프를 중단한다. `degraded`는 결과를 사용하되 완료 보고에 남긴다. `gap` subagent는 내부에서 다시 dispatch하지 않는다.

### Phase B — gap을 이슈로 (fresh subagent)

위 "Phase B·C 위임" 절이 정한 방식으로 `gap`을 수행할 subagent를 dispatch한다(수행 문서: 이 디렉터리의 `gap.md`).
gap은 문서 대비 gap을 **이슈로 등록하며, 같은 gap을 다루는 이슈가 있으면 그쪽에 접는다**(중복 제거 내장). 전역 모드는 새로 만든 빌드가능 이슈를 `Ng`로 기록한다. 이슈 범위 모드는 `scope_additions`의 이번 라운드 최초 편입 번호만 scope 큐에 센다.

`fallback`은 `degraded`로 정규화한다. `blocked`·`degraded` 처리는 위 반환 계약을 따른다.

### Phase B' — design-review를 이슈로 (fresh subagent, 보고 전용)

**persona보다 먼저 돈다.** 시각적 결함이 남아 있으면 persona가 "헷갈린다"고 보고할 때 그것이 흐름
문제인지 그냥 다듬어지지 않은 것인지 갈리지 않는다. 먼저 다듬을 목록을 뽑고, 그 다음에 흐름을 태운다.

**이 Phase의 발견도 큐에 들어간다 — `gap`·`persona`와 같다.** `design-review`가 잡는 것은
취향이 아니라 **일관성 결함**이다(간격이 어긋난 버튼, 위계가 깨진 화면). 디자인 시스템이
자리 잡으면 줄어들므로 끝이 있고, 그러면 평범한 결함이고 평범한 백로그다.

- **게이팅**: 이번 라운드의 build가 **UI를 건드리지 않았으면 건너뛴다.** 판정은 라운드 중 머지된 PR의
  변경 파일로 한다. 건너뛴 사실을 한 줄로 보고한다.
- **`design-review` 스킬이 없으면 건너뛴다.** 중단이 아니다 — 품질 축이 빠질 뿐 루프는 계속 돈다.
- 위 "Phase B·C 위임" 절이 정한 방식으로 fresh subagent에 위임한다. dispatch 프롬프트에 **아래 둘을 반드시
  명시한다**:
  - **"보고 전용이다 — 발견을 이슈로만 남긴다."** `design-review`는 기본적으로 고치는 스킬이다. 고치면
    (a) 다음 build가 0단계 미커밋 검사에서 멈추고 (b) 리뷰·PR 게이트를 우회해 코드가 들어간다.
  - **"발견을 이슈로 등록하라"** — 동일성 키로 중복 제거하고, `design-debt` 라벨을 단다. 이 라벨은
    **분류용이지 제외용이 아니다** — 플래그 없는 `build`가 평범한 구현 대상으로 집는다.
    라벨 부착 실패는 등록 실패다.

**반환 계약**: `design_ran` (true/false + false면 사유) / 만든 이슈 전체(번호·제목) / **그중 빌드가능
번호 목록** / 중복이라 안 만든 수 / `degraded` / 이슈 범위 모드면 `scope_additions`.
**`Nd`는 `gap.md`·`design-review`에 없는 개념이므로 이 표를 dispatch 프롬프트에 그대로 붙여 넘긴다** —
안 넘기면 원시 이슈 수를 `Nd`로 쓰거나 없는 값을 0으로 읽어 거짓 수렴한다.

**`design_ran=false`는 수렴을 막지 않는다.** persona와 다른 점이다 — persona 미검증은 "흐름을 안 봤다"라
수렴 근거가 못 되지만, design은 **스킬이 없거나 UI 변경이 없어서** 안 도는 것이 정상 경로다.
그 라운드는 0으로 치고 사유를 보고에 남긴다.

### Phase C — persona를 이슈로 (fresh subagent, 서비스 기동도 subagent가)

위 "Phase B·C 위임" 절이 정한 방식으로 `persona-test`를 수행할 subagent를 dispatch한다(수행 문서:
`gritive:persona-test`의 `SKILL.md`). **서비스 기동·브라우저 구동·발견·이슈 등록은 그 subagent가 자기
컨텍스트에서 직접 한다** — 이 세션은 반환만 읽는다. dispatch 프롬프트에 "먼저 대상 `CLAUDE.md`의 실행
명령(또는 `run` 스킬)으로 앱을 띄우고 접근 인터페이스(web URL/CLI)를 확인한 뒤 persona-test를 수행하라.
기동하지 못하면 `persona_ran=false` + 사유로 반환하라"를 명시한다.

- subagent가 `persona_ran=true`를 돌려주면 전역 모드는 새로 만든 빌드가능 이슈를 `Np`로 기록한다. 이슈
  범위 모드는 `scope_additions`의 이번 라운드 최초 편입 번호만 scope 큐에 세고 `persona_ran = true`로 표시한다.
- **접어 넣은 열린 이슈 번호는 "핵심 개념" 절의 큐 공식대로 `Np`에 더한다.** 공식이 빼는 번호는
  **"루프가 소비할 수 없는 이슈"로 종료 보고에 적는다** — 조용히 빼면 관측된 파손이 사라진 것과 같다.
- `persona_ran=false`·`coverage=partial`·`blocked`·`degraded` 처리는 위 반환 계약 절이 정한다.

**persona가 안 돈 라운드의 "발견 0"은 수렴 신호가 아니다.** 검사를 안 했으므로 "깨끗함"을 증명하지
못한다. 수렴 종료(Phase D)는 **persona가 실제로 돈 라운드에서만** 선언할 수 있다.

## Phase D — 수렴·정체·중단 판정

라운드가 끝나면(A~C 모두 통과, build 중단 없음) 판정한다:

- **수렴(종료)**: 전역 모드는 이번 라운드의 새 빌드가능 이슈가 0, 이슈 범위 모드는 `issue-scope.md`의
  scope 큐와 미완료 buildable이 모두 0, 그리고 `persona_ran == true`. → 완료 보고를 내고 끝낸다.
- 아니면 다음 라운드로. 단 아래 중 하나면 **멈추고 보고한다**:

| 중단 조건                                                                     | 이유                                                           |
| ----------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 라운드 수가 상한(기본 10) 도달                                                | 무한 루프 방지 backstop                                        |
| build가 **중단 조건**으로 멈춤 (위 `outcome` 표)                                    | 구현하다 막혔다(사용자 결정 필요 포함). 사유를 그대로 올리고 멈춘다 |
| **같은 동일성 키 이슈가 build됐는데 다음 라운드 gap/persona가 또 만듦** (3회) | 고쳤는데 또 나온다 = 수정이 문제를 해결하지 못한다             |
| **새 빌드가능 이슈 수가 두 라운드 연속 줄지 않음** (0이 아닌 채로)            | 코드가 성숙하는데 발견이 안 줄면 접근이 틀렸다                 |
| persona가 **매 라운드 기동 실패**해 상한까지 한 번도 검증 못 함               | 클린을 증명할 수 없다. "persona 미검증으로 클린 미도달"로 보고 |
| gap/persona가 `blocked`를 반환 (강등 경로 없는 질문에 막힘)                   | 그 질문을 사용자에게 올리고 루프를 멈춘다. 수렴이 아니다        |
| persona가 `coverage=partial` (강등이 테스트 범위를 줄임)                      | 그 라운드는 미검증이다 — 수렴 선언은 `persona_ran == true`인 라운드에서만 한다 |

**동일성 키는 gap/persona가 정하는 키를 그대로 쓴다** — gap은 "요구사항 + 근거 문서 위치", persona는
`persona-test`가 정한 키다. 코드를 고치면 라인·심각도가 흔들리므로 어느 키에도 넣지 않는다. 그래야
"고쳤는데 또 나온 것"만 반복으로 잡힌다.

**정체·반복은 실행 큐로만 잰다** — 큐 공식과 그 예외는 "핵심 개념" 절이 정한다.
이 판정에 도달했다는 것은 각 build가 `drained` 또는 미완료 에픽 없는 `excluded_only`였다는 뜻이다.
미완료 에픽은 build 단계에서 `stopped`가 되어 이 판정까지 오지 않는다.

## 출력 계약

- **라운드별 로그·요약은 대화로 출력한다.** persona의 스크린샷 등은 `persona-test`의 산출물 디렉토리에
  남는다 — 그 문서가 기준이고 경로를 여기 옮겨 적지 않는다.

## 완료 보고

**수렴한 즉시, 또는 멈춘 즉시** 대화에 요약을 낸다:

- 돈 라운드 수와 **라운드별 실행 큐 크기** (예: `큐 8 → 3 → 0`). gap/persona의 원시 발견 수를 함께
  적되 **둘을 구분한다**.
- 라운드별로: build가 소진한 이슈, gap이 만든 빌드가능 이슈(번호), design이 만든 빌드가능 이슈(번호), persona가 만든 빌드가능 이슈(번호),
  persona 검증 여부(미검증이면 사유).
- **에픽 게이트 결과** — 게이트를 돈 에픽 번호마다 만든 형제 이슈 번호와 persona 실행 여부(안 돌았으면
  사유). 이 게이트가 조기 피드백의 산출물이므로 안 적으면 라운드 요약만으로는 보이지 않는다.
- **제외 클래스로 빠진 것** — 만들어졌지만 큐에 안 든 `question`·`credential` 이슈 번호. 사람·고객이 볼 것.
- **"루프가 소비할 수 없는 이슈" 번호** — persona가 관측을 접어 넣은 열린 이슈인데 두 라운드 연속
  build가 안 태워 큐에서 뺀 것(Phase C). 없으면 "없음"이라고 적는다. **관측으로 확인된 파손인데 루프가
  못 고치는 것이므로 사람이 왜 build가 건너뛰는지 봐야 한다** — 안 적으면 조용히 사라진다.
- **Phase B' 결과**: `design-review`가 돌았는지(안 돌았으면 사유 — 스킬 없음 / UI 변경 없음),
  만든 `design-debt` 이슈 번호와 **그중 큐에 넣은 수**.
- **`build-blocked` 처리된 이슈 번호와 사유** (build 완료 보고의 해당 항목). 없으면 "없음"이라고 적는다 —
  이건 루프가 포기한 일감이므로 사람이 이슈를 고치고 라벨을 떼야 돌아온다. 안 적으면 조용히 사라진다.
- build가 종결한 에픽 번호. 미완료 에픽 때문에 멈췄으면 에픽 번호와 막힌 leaf·해제 조건.
- 수렴했으면 "마지막 라운드에서 gap·design·persona 모두 새 빌드가능 0, persona 실제 실행됨"을 명시한다.
- **수렴 못 했으면 왜 멈췄는지**(상한 도달 / build 중단 / 정체 / persona 미검증)와 남은 위험.

**수렴은 persona가 실제로 검증된 라운드에서만 선언한다.** build가 중단해서 끝났으면 그 사유를 그대로
전하고 중단으로 보고한다.
