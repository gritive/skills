# project gap

`/project gap` — RFP·PRD·design-guide(및 별도 UX 가이드가 있으면 그것도)와 **실제 구현(코드)** 사이의 gap을 분석한다. 문서끼리 비교하는 게 아니라, 각 요구사항이 코드에 실제로 있는지를 fresh eye로 검증하고, 구현된 기능이 화면(UI)까지 노출됐는지를 별도로 확인한다.

## 입력

- 인자를 받지 않는다. 대상은 **현재 작업 디렉터리**다.

## 절차

### 1. 근거 문서 확정

- 대상 `CLAUDE.md`의 "문서 라우팅" 표를 읽어 RFP/PRD/design-guide/(있으면) 별도 UX 가이드의 실제 경로를 확인한다.
- 표에 없으면 `docs/RFP.md`, `docs/prd.md`, `docs/design-guide.md`, `docs/ux-guide.md` 등 통상 경로를 시도하고, 그래도 못 찾으면 사용자에게 묻는다.
- design-guide 안에 UX 기준이 통합돼 있으면(문서 라우팅 표에 "UI/UX/접근성"이 design-guide 하나로 묶여 있는 경우 등) 별도 문서를 찾지 않는다.

### 2. fresh eye subagent에 위임 (본 세션에서 직접 분석하지 않는다)

- Agent 툴로 새 subagent를 dispatch한다. **이 단계를 생략하고 현재 대화 맥락에서 바로 분석하지 않는다.**
- 이유: 진행 중인 세션에는 이전 세션 요약, CLAUDE.md/README의 "구현 완료" 자체 서술 같은 선입견이 이미 쌓여 있다. 같은 컨텍스트에서 이어서 분석하면 그 선입견을 그대로 따라가 실제로는 미완성인 부분을 완료로 오판하기 쉽다. 사전 지식 없는 새 subagent가 처음부터 코드를 읽게 한다.
- subagent 프롬프트에 반드시 아래 다섯 가지를 명시한다:
  1. RFP → PRD → design-guide(+UX 가이드) 순으로 읽고, 각 문서가 요구하는 기능/요구사항을 **빠짐없이** 항목화한다. 눈에 띄는 몇 개만 골라 확인하지 않는다.
  2. 각 항목마다 실제 코드(`src/**`, 서비스 디렉터리 등)를 열어 구현 여부를 확인한다. **문서·주석·CLAUDE.md의 자체 서술("구현 완료", "부분 구현" 등)을 근거로 삼지 말고, 실제 코드·라우트·함수가 존재하고 동작하는지로 판정**한다.
  3. 구현된 항목에 한해, 그 기능에 도달하는 화면 진입점(라우트, 컴포넌트, 버튼/폼)이 있는지를 **별도로** 확인한다. "구현됨"과 "화면에 노출됨"을 하나로 뭉치지 않는다 — API/서비스 레벨에서는 동작하지만 어떤 화면에서도 호출·노출되지 않는 항목(백엔드만 존재)을 명시적으로 구분해낸다.
  4. 모든 판정에 근거(파일 경로, 필요하면 함수명·라인)를 남긴다. 근거를 찾지 못하면 미구현으로 판정한다.
  5. design-guide에 "인터랙션 패턴"(상호작용 규약)이 있으면, 구현·노출된 화면이 그 규약을 실제로 따르는지 확인한다. 규약과 어긋나거나(예: 규약은 삭제 확인인데 즉시 삭제) 같은 부류의 상호작용이 화면마다 제각각인 것도 gap이다 — 문서엔 규약이 있는데 코드가 안 지키는 것이므로 "문서 간 불일치"가 아니라 **실행 가능한 gap**으로 분류한다. 규약값(파일 위치)과 실제 화면 동작(파일 경로)을 함께 근거로 남긴다. 규약이 Storybook 정본 story로 실현돼 있으면, 화면이 그 정본 컴포넌트를 재사용하는지(규약을 화면마다 재구현하지 않았는지)를 근거로 본다. 인터랙션 테스트를 채택한 프로젝트(design-guide 인터랙션 절에 `인터랙션 테스트: 채택`)면 테스트의 존재·통과 여부까지 확인하고, 미채택이면 이 사후 리뷰가 규약 준수의 강제 지점이다. **UI가 있는 제품인데 design-guide에 이 절이 아예 없으면 "확인할 규약이 없음"으로 넘기지 말고, 그 사실 자체를 결과에 올린다** — 규약이 없으면 이 점검도 `build`의 정본 story backfill도 통째로 발동하지 않으므로, `/project sync` 4단계로 규약 절을 채워야 한다고 보고한다.

### 3. 결과 정리

- 다음 열로 표를 만든다: 요구사항 / 근거 문서 위치 / 구현 여부(구현·부분구현·미구현) / UI 노출 여부(노출·미노출·해당없음) / 근거(파일 경로) / 비고.
- **"구현됐지만 UI 미노출"** 항목을 별도 섹션으로 강조한다 — 이 명령의 핵심 관심사다.
- **인터랙션 규약 위반**(구현·노출됐지만 design-guide 상호작용 규약과 다르게 동작하거나 화면 간 상호작용이 불일치)도 별도 섹션으로 강조한다. 규약 대비 실제 동작·근거 파일을 함께 적는다.
- 문서 간 자체 불일치(RFP vs PRD vs design-guide)도 발견되면 별도 섹션에 남긴다.

### 4. gap을 이슈로 등록 (문서를 만들지 않는다)

gap 분석 리포트는 **부산물**이므로 별도 문서로 남기지 않는다. 실행 가능한 gap은 이 프로젝트의 **이슈 관리 방식**에 따라 이슈로 등록한다. 이슈 생성 패턴은 `prd-to-issue.md`와 동일하다.

먼저 이 프로젝트에 이슈 관리 방식이 있는지 확인한다:

- 대상 `CLAUDE.md`의 "이슈 관리" 섹션을 읽어 org/보드/마일스톤·연결 방식·라벨 컨벤션을 파악한다(`prd-to-issue.md` 2단계와 동일). **org/보드 번호를 이 문서에 하드코딩하지 않는다** — 항상 대상 CLAUDE.md에서 읽는다.
- "이슈 관리" 섹션이 없거나 `gh`가 인증돼 있지 않으면 **이슈 관리 방식이 없는 것으로 보고 아래 "이슈 관리 방식이 없을 때"로 간다.**

이슈 관리 방식이 있으면:

1. **기존 이슈 컨벤션·중복 확인** — `gh issue list --state all`로 이미 만들어진 이슈를 보고, 대표 이슈 2~3개 본문(`gh issue view <n>`)으로 제목 접두 분류·본문 섹션 구조·의존 표현·보드 연결 컨벤션을 답습한다. 추측하지 않는다. **같은 gap을 이미 다루는 이슈가 있으면 새로 만들지 않는다.**
2. **실행 가능한 gap**(미구현·부분구현·"구현+UI 미노출"·인터랙션 규약 위반)을 각각 이슈로 만든다. 본문에 근거 문서 위치, 현재 구현 상태(근거 파일 경로), 필요한 작업, 판정 근거를 남긴다. "구현+UI 미노출"은 **UI 진입점 추가가 작업**이므로 그 점을 본문에 명시한다("백엔드/서비스는 있으나 어떤 화면에서도 호출·노출되지 않음"). "인터랙션 규약 위반"은 **규약에 맞춰 화면 동작을 고치는 것이 작업**이므로 규약값과 현재 동작을 함께 명시한다.
3. **문서 간 자체 불일치**(RFP vs PRD vs design-guide)는 코드 작업이 아니라 어느 문서를 기준으로 삼을지 **사용자·고객이 정해야 할 결정**이므로 `question` 라벨 이슈로 만든다(라벨 없으면 `gh label create question`). 리포에서 쓰는 결정용 라벨 컨벤션이 따로 있으면 그쪽을 따른다.
4. 각 이슈 생성 직후 1단계에서 확인한 규칙대로 보드에 연결한다.

### 이슈 관리 방식이 없을 때 (폴백)

- 이슈를 만들지 말고 3단계 표를 **대화로** 리포트한다.
- 파일(`docs/gap-analysis.md` 등)로 남길지는 사용자에게 먼저 확인한다(기존 파일 있으면 갱신 여부도 확인). 확인 없이 대상 저장소에 파일을 만들지 않는다.

## 완료 보고

- 전체 요구사항 수, gap 개수, 그중 "구현+UI 미노출" 개수를 요약하고 핵심 워크플로우 차단 여부로 우선순위를 붙인다.
- **이슈로 등록한 경우**: 만든 이슈 번호·제목·유형(미구현/부분구현/UI 미노출/인터랙션 규약 위반/문서 불일치)을 표로 요약하고, 중복이라 만들지 않은 항목도 명시한다.
- **폴백(리포트)한 경우**: 위 요약을 대화로 출력하고, "이슈 관리 방식이 없어 리포트로 갈음했다"고 밝힌다.
