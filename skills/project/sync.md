# project sync

`/project sync` — 공유 baseline이 갱신됐을 때, 프로젝트 **CLAUDE.md**(2~3단계)와 **design-guide의
인터랙션 규약 절**(4단계)에 **빠진 공유 baseline만** 보강한다. 섹션 통째뿐 아니라 **기존 섹션 안에
새로 생긴 불릿**까지 backfill한다.

**README는 대상이 아니다.** README 템플릿의 모든 섹션(구성/기술스택/시작하기/문서)이 프로젝트 고유
슬롯이라 밀어넣을 공유 baseline이 없다 — README에 대해서는 이 커맨드가 할 일이 없다.

## 묻지 못하는 실행 (강등)

이 문서의 절차는 여러 곳에서 사용자에게 묻는다. subagent에는 `AskUserQuestion`이 없으므로(예: `project loop`이 dispatch한 경우) 그때는 다음으로 대체한다.

- 물어야 확인되는 **추가·삽입은 하지 않고** 넘어간다(섹션 제목 추가, 슬롯 값 채우기, Storybook 도입 여부, `인터랙션 테스트:` 한 줄, 애매한 불릿). 확인 없이 넣지 않는 것이 additive-only의 기본값이다.
- 넘어간 항목은 무엇을 왜 못 채웠는지 함께 `degraded`로 반환한다.
- 대상 `CLAUDE.md`가 없어 diff 대상이 아예 없으면 `blocked`으로 반환한다.

## 원칙 (additive-only)

- 템플릿 → 프로젝트 방향으로만 흐른다. 프로젝트 고유 내용은 절대 덮어쓰지 않는다.
- 두 종류의 섹션을 구분한다:
  - **공유 baseline 섹션** — Clean Architecture 원칙 / God Object 방지 / 개발 원칙 / 이슈 관리 / Architecture / 구현 기준. 프로젝트에 공통 적용되는 baseline 불릿을 담는다. 여기를 **불릿 단위로 보강**한다.
  - **프로젝트 고유 슬롯 섹션** — 문서 라우팅 / Commands / 도메인 용어. 공유 소스가 없으므로 내용을 밀어넣지 않는다. 섹션 제목 자체가 통째로 없을 때만 사용자에게 추가 여부를 확인한다.

## 절차

### 1. 템플릿과 프로젝트 문서 읽기

- **이 스킬 디렉터리의** `templates/CLAUDE.md.template` (대상 프로젝트 cwd 기준 상대 경로가 아니다).
- 대상 `CLAUDE.md`.

### 2. 섹션 단위 diff

- 템플릿의 각 `##` 섹션 제목을 목록화한다.
- 프로젝트에 그 제목(또는 의미상 대응 섹션)이 **없으면**:
  - 공유 baseline 섹션이면 템플릿 원문을 삽입 후보로 둔다. 단 **`{{…}}` 슬롯과 `<!-- setup: … -->`
    주석을 그대로 써넣지 않는다** — 이슈 관리·Architecture·구현 기준 섹션은 슬롯을 품고 있다.
    주석은 지우고, 슬롯은 사용자에게 값을 물어 채운 뒤 삽입한다. 값을 못 얻으면 그 줄을 뺀다.
  - 프로젝트 고유 슬롯 섹션이면 사용자에게 확인(내용은 채우지 않는다).

### 3. 불릿 단위 diff (공유 baseline 섹션만)

- 프로젝트에 이미 있는 각 공유 baseline 섹션에 대해, 템플릿의 baseline 불릿을 하나씩 본다.
- 템플릿 불릿이 담은 **아이디어**가 프로젝트 섹션에 없으면 그 불릿을 추가한다.
- 프로젝트에 같은 아이디어의 불릿이 이미 있으면(문구가 다르거나 더 상세해도) **중복 추가하지 않는다**. 프로젝트는 대개 템플릿의 상위 집합이라 대부분 이미 존재한다.
- baseline 불릿이 `{{…}}` 플레이스홀더를 품은 경우(예: 이슈 관리의 보드 대상), **아이디어**로 매칭한다 — 프로젝트에 구체 값으로 채워진 대응 불릿이 있으면 이미 존재로 본다.
- 판단이 애매하면 추가하지 말고 사용자에게 확인한다.
- **완료 조건: 템플릿의 baseline 불릿 전건에 대해 추가 / 이미 존재 / 보류(사용자 확인) 중 하나를
  판정한다** — 판정하지 않은 불릿이 0건일 때 이 단계가 끝난다.

### 4. design-guide 인터랙션 규약 backfill (`docs/design-guide.md`)

`build`의 Storybook 표준 story backfill과 `gap`의 규약 준수 리뷰는 둘 다 design-guide가 규약을 선언했을 때 발동한다. 이 단계는 규약 절이 없는 기존 프로젝트에 그 절을 채워 두 기능이 발동하게 한다.

- 대상에 `docs/design-guide.md`가 **없으면 건너뛴다.** 여기서 design-guide를 새로 만들지 않는다 —
  그건 `setup` 5단계의 일이다.
- design-guide가 있고 **"인터랙션 패턴" 절이 없으면** 그 절을 additive로 더한다. 보강 내용은
  **이 스킬 디렉터리의 `references/interaction-baseline.md`를 읽어 수행한다.**
- **기존 저장소이므로 `setup.md` 5단계의 brownfield reconcile 규칙을 그대로 적용한다.**
- **컴포넌트형 웹인데 스택에 Storybook이 없으면 규약 표까지만 채우고 끝내지 않는다.** `build`의 표준
  story backfill은 design-guide의 **story 선언**을 전제로 하므로, 표만 채우면 이 커맨드가 메우려던
  구멍이 그대로 남는다. 사용자에게 Storybook 도입 여부를 묻고 — **도입하면** `setup.md` 2단계대로
  CLAUDE.md 기술 스택·Commands에 넣고 5단계대로 표준 story 목록을 선언한다(story 파일 자체는 만들지
  않는다 — 그건 `build`가 UI Req에서 한다). **도입하지 않으면** 규약 표까지만 두되, "story가 없으므로
  규약 준수는 `gap` 사후 리뷰가 유일한 강제 지점"임을 보고에 남긴다.
- **design-guide의 다른 절은 건드리지 않는다.** 인터랙션 패턴 절만 더한다.
- 절이 이미 있으면 내용은 두고, 머리줄의 `인터랙션 테스트: 채택|미채택` 한 줄이 **없을 때만** 사용자에게
  물어 그 줄을 추가한다 — `build`·`gap`이 이 값을 읽으므로 비면 판정이 불가능하다.
- 규약에서 벗어난 화면(divergence)을 **이슈로 만드는 것은 `gap`이 한다.** sync는 규약을 채워 넣을 뿐이다.

### 5. 보고

- 추가한 섹션·불릿과 "이미 존재해 건드리지 않은" 항목을 함께 보고해, 파괴적 변경이 없음을 확인시킨다.
- design-guide를 건드렸으면 무엇을 추인하고 무엇을 baseline으로 채웠는지 함께 보고한다.
