# project setup

`/project setup <RFP-path>` — RFP 한 장에서 프로젝트의 기획·기준 문서를 생성한다. 리서치 subagent(2·5단계)와 fresh-eye subagent(7단계)를 **오케스트레이션**한다. 이 세션에서 직접 웹을 뒤지거나 gap 분석을 재구현하지 않는다.

## 입력

- `<RFP-path>`: RFP 마크다운 경로(예: `docs/RFP.md`). 없으면 사용자에게 묻는다.

## 절차

### 1. RFP 읽기

- RFP를 Read로 읽고 도메인·목표·주요 요구·제약을 파악한다.

### 2. research #1 — 도메인/시장/베스트프랙티스

- Agent 툴로 리서치 subagent를 1회 dispatch한다 — `subagent_type="general-purpose"`(웹 툴을 가진 범용 에이전트가 필요하다. 이 플러그인의 리뷰 에이전트는 읽기 전용이라 쓰지 않는다). research question 예: "{도메인} 서비스의 표준 기능 범위, 경쟁 제품, 데이터 모델 관례, 운영 워크플로우 베스트프랙티스는?"
- 프롬프트 규약: `WebSearch`·`WebFetch`로 **최소 5개 출처**를 모으고, `## 표준 기능 범위`·`## 경쟁 제품`·`## 데이터 모델 관례`·`## 운영 워크플로우` 네 절로 **항목마다 출처 URL을 단** 마크다운 요약을 **반환 텍스트로만** 돌려준다(파일을 쓰지 않는다). 웹 접근이 없으면 그 사실을 머리에 밝히고 근거 없는 항목을 지어내지 않는다.
- **반환을 검사한 뒤 저장한다.** 검사 결과는 셋 중 하나이고, 갈리는 것은 **subagent가 돌긴 했는가**다:

| 반환 | 처리 |
| --- | --- |
| 절 구조가 있고 출처 URL이 붙어 있다 | `docs/research/domain-research.md`로 저장(디렉터리 없으면 생성). 출처가 5개 미만이면 저장하되 **노트 머리에 개수를 적고** 그 항목은 이후 `[관례]`로 표기한다 |
| 돌았지만 **웹 접근이 없었다**고 밝혔다 | 저장한다. **노트 머리에 "웹 접근 없음"을 남긴다** — 이후 신뢰도 표기가 `[소스]`가 아니라 `[관례]`인 근거다. 이것이 `SKILL.md`가 말하는 강등이다 |
| **아예 안 돌았다** — dispatch 실패(Agent 툴 없음·깊이 상한), 빈 반환, 오류 메시지 | **저장하지 않는다.** 1회 재dispatch하고 두 번째도 같으면 노트를 만들지 말고 **사용자에게 알린 뒤 멈춘다** |

- 셋째 줄만 중단이다. **"출처 URL이 없다"는 것만으로 판정하지 마라** — 웹 접근이 없어 못 단 것(강등)과 subagent가 안 돈 것(중단)은 겉보기가 같고 처리가 다르다. 노트 머리의 자기 보고로 가른다.
- 이 검사를 건너뛰면 오류 메시지나 빈 노트가 `docs/research/`에 남고, 4·6단계가 그것을 근거로 인용한다. **저장된 노트는 곧 근거라는 것이 이 단계의 계약이다.**

### 3. 기술스택·툴체인 확정

- RFP가 스택을 명시하면(예: "SvelteKit 기반") 그대로 채택한다. 명시가 없거나 불완전하면 도메인·요구에 맞게 **결정**한다.
- 언어·프레임워크만이 아니라 이후 슬롯이 요구하는 세부까지 정한다: 패키지 매니저, ORM/DB, 마이그레이션·시드·테스트 명령 세트, **UI 계층(CSS 프레임워크·컴포넌트 라이브러리)**, **인증/인가 계층**. UI가 있는 제품이면 CSS 프레임워크·컴포넌트 라이브러리를 반드시 확정해 `{{TECH_STACK}}`에 넣는다 — 프레임워크만 적고 스타일링·컴포넌트 계층을 빠뜨리지 마라. **컴포넌트형 웹 프론트(React/Vue/Svelte 등 컴포넌트 라이브러리를 쓰는 경우)면 컴포넌트·인터랙션 워크샵으로 Storybook을 확정해 `{{TECH_STACK}}`·`{{COMMANDS}}`에 넣는다** — 6단계 인터랙션 규약의 정본 story가 여기 얹힌다. 서버 렌더 템플릿(Jinja·Go template)이거나 비웹이면 Storybook은 넣지 않는다(그 경우 규약은 markdown 결정 표까지만). 로그인·세션·역할 기반 접근제어(RBAC)가 필요하면 인증 라이브러리도 반드시 확정해 넣는다 — RBAC UX가 design-guide에 있는데 인증 스택이 비면 안 된다. 이 결정이 이후 `{{TECH_STACK}}`·`{{COMMANDS}}`·`{{GETTING_STARTED}}`와 5단계 research question의 `{기술스택}` 근거다.
- 언어가 Python이면(RFP가 다른 웹 프레임워크·ORM·패키지 매니저를 명시하지 않는 한) 웹 프레임워크는 FastAPI, ORM은 SQLAlchemy, 패키지 매니저는 uv를 기본값으로 채택한다.
- 언어가 Go이면(RFP가 다른 웹 프레임워크·ORM을 명시하지 않는 한) 웹 프레임워크는 Echo, ORM은 GORM을 기본값으로 채택한다.
- 언어가 JavaScript/TypeScript(Node.js)이면(RFP가 다른 프레임워크·ORM·패키지 매니저를 명시하지 않는 한) 프레임워크는 SvelteKit, ORM은 Drizzle, 패키지 매니저는 bun을 기본값으로 채택한다. 인증이 필요하면 Better Auth를 기본값으로 채택한다(TS-네이티브, Drizzle·SvelteKit과 통합; RFP가 다른 인증 스택을 명시하지 않는 한). SvelteKit에 UI가 있으면 CSS는 Tailwind CSS, 컴포넌트 라이브러리는 shadcn-svelte를 기본값으로 채택한다(RFP가 다른 스타일링·컴포넌트 스택을 명시하지 않는 한). PRD에 복잡한 데이터 테이블/그리드(정렬·필터·페이지네이션·컬럼 제어)가 있으면 TanStack Table을 추가한다(shadcn-svelte data-table이 그 위에 얹혀 있다). 클라이언트 상태 상호작용(낙관적 업데이트·백그라운드 refetch/폴링·페이지 간 클라이언트 캐시·dependent/infinite query)이 있으면 TanStack Query를 추가한다. 단순 페이지 데이터 페칭·라우팅은 SvelteKit `load`/`invalidate`로 충분하므로, 그 수준이면 TanStack Query/Router를 기본 채택하지 않는다.

### 4. PRD 생성 또는 갱신 (`docs/prd.md`)

- RFP + research #1을 근거로 작성한다. 이미 `docs/prd.md`가 있으면 research 결과를 **반영(갱신)** 하되 기존 결정 이력을 보존한다.
- 필수 섹션 스켈레톤:
  1. 개요 (배경 / 목표 / 1차 범위 원칙)
  2. 사용자와 역할
  3. 기능 요구사항 (기능별 소절)
  4. 1차 범위 제외 (향후 검토)
  5. 비기능 요구사항
  6. 데이터 모델 개요
  7. 결정 사항 — 채택 스택(3단계)과 미확정 이슈(`Q1..Qn`)를 기록한다

### 5. research #2 — 디자인/UX

- 2단계와 같은 규약(같은 `subagent_type`, 최소 출처 수, 항목마다 출처 URL, **반환 텍스트로만** — 파일을 쓰지 않는다, 반환 검사와 실패 처리)으로 리서치 subagent를 1회 더 dispatch한다. **절 구조만 이 질문에 맞춰 바꾼다**: `## 인터랙션 관례`(baseline을 벗어나는 것)·`## 컴포넌트 매핑`·`## 접근성(WCAG AA)`. 2단계의 도메인용 절 제목을 그대로 가져오지 않는다. research question 예: "{제품 유형}의 데이터 테이블/폼/대시보드/RBAC UX 베스트프랙티스, **이 제품 성격에서 6단계 인터랙션 baseline을 벗어나는 관례**(예: 페이지네이션 vs 무한스크롤, 필터 라이브 vs 적용 버튼, 삭제 확인 vs undo 중 이 도메인이 다르게 하는 것), {기술스택} 컴포넌트 매핑, WCAG AA 기준은?"
- 인터랙션 규약 자체는 6단계 baseline에서 결정한다. 이 리서치는 그 baseline을 **조정할 근거**(제품 성격 특유의 관례·라이브러리 지원 패턴)를 대는 용도다 — 규약을 처음부터 리서치로 만들지 않는다.
- 2단계와 같은 세 갈래 검사를 거쳐(절 구조는 위 세 절 기준) `docs/research/design-research.md`로 저장한다. 안 돈 경우에만 멈춘다.

### 6. 디자인·UX 가이드 생성 (`docs/design-guide.md`)

- RFP + PRD + research #2로 작성. 각 근거에 신뢰도 표기(`[소스]` / `[검증]` / `[관례]` / `[PRD]`)를 단다.
- **`[소스]`는 리서치 노트에 그 항목의 출처 URL이 실제로 있을 때만 단다.** 노트 머리에 "웹 접근 없음" 또는 "출처 N개(5 미만)"이 적혀 있으면 해당 항목은 `[관례]`다 — 노트 머리를 먼저 읽고 표기를 정한다.
- 필수 섹션 스켈레톤: 핵심 원칙 / 디자인 토큰 / **인터랙션 패턴** / 데이터 테이블 / 입력 폼 / 대시보드 / RBAC UX / 공통 상태(로딩·빈·오류) / 접근성 체크리스트 / 컴포넌트 인벤토리 / 출처.
- **"인터랙션 패턴"은 프로젝트 전역 상호작용 규약이다.** 시각 토큰이 "무엇이 어떻게 보이는가"를 고정하듯, 이 절은 "무엇이 어떻게 동작하는가"를 고정한다. 되풀이되는 상호작용 부류마다 프로젝트 전체에 걸쳐 **답을 하나만** 정하고, 아래 컴포넌트 절(데이터 테이블·입력 폼 등)은 그 답을 **다시 정하지 말고 참조만** 한다. 이 단일 출처가 없으면 한 화면은 생성이 모달인데 옆 화면은 페이지, 삭제는 여기선 확인·저기선 즉시가 되어 어긋난다.
- **규약은 리서치 요약이 아니라 결정이다.** 3단계에서 기술스택을 리서치가 아니라 의견 있는 기본값으로 정했듯, 인터랙션도 baseline 규약을 기본값으로 채택하고 필요한 곳만 조정한다. **단, baseline은 한 벌이 아니라 제품 성격별로 다르다** — UX·인터랙션은 제품 성격에 따라 크게 갈리므로, 성격을 먼저 분류해 그 성격의 baseline을 채택한다. 순서:
  1. **제품 성격 분류 + 필요한 부류 도출** — PRD의 기능·데이터·사용자로 제품 성격을 판단하고(아래 성격 중 하나, 판단 근거를 한 줄로 남긴다), 그 제품에 실제로 있는 상호작용 부류만 규약 대상으로 삼는다. 없는 부류(예: 벌크 액션이 없는 제품의 벌크 규약)는 만들지 않는다.
  2. **해당 성격의 baseline 채택** — 아래 기본값을 그대로 design-guide에 옮긴다.
  3. **라이브러리·특수 요구로 조정** — 3단계 `{{TECH_STACK}}` 컴포넌트 라이브러리가 실제로 미는 패턴, PRD의 특수 요구에 맞춰 baseline을 덮어쓴다. 라이브러리가 안 미는 상호작용을 규약으로 박지 않는다. research #2는 이 조정의 **근거를 댈 때만** 쓴다 — baseline을 매번 리서치로 다시 만들지 않는다.
  4. **결정 표로 기록** — 상호작용 / 채택 규약 / 근거·신뢰도 / 예외.
- **성격별 baseline.** 아래 부류를 모두 다룬다(제품에 없는 부류만 생략). `사내 admin/백오피스 CRUD`를 기본 성격으로 삼고, 제품이 다른 성격이면 그 열의 값으로 바꾼다:

  | 부류 | 사내 admin/백오피스 CRUD (기본) | 소비자 대면·모바일 우선 | 데이터·분석 대시보드 |
  | --- | --- | --- | --- |
  | 목록 규모 | 서버 페이지네이션(25행/page, 총건수 노출) | 무한 스크롤/더 보기 | 페이지네이션 + 대용량은 가상 스크롤 |
  | 필터·검색 | 라이브 적용(디바운스 300ms), 상태를 URL 쿼리에 반영, 명시적 초기화 | 라이브 + 하단 시트 필터 | 적용 버튼(조회가 무거움) + URL 반영 |
  | 정렬 | 헤더 클릭 단일 정렬 | 프리셋 정렬 드롭다운 | 다중 정렬·컬럼 제어 |
  | 생성/편집 | 필드 6개↓·의존관계 없음 → 모달, 그 이상·다단계·파일 → 전용 페이지, 단일 필드 → 인라인 | 전용 화면·스텝 폼 | 주로 읽기; 생성은 모달/사이드패널 |
  | 삭제·파괴적 액션 | soft delete → undo 토스트, 되돌리기 불가·연쇄 영향 큼 → 확인 다이얼로그(대상명), 대량·영구 → 타이핑 확인 | 스와이프 + undo 스낵바 | 확인 다이얼로그 기본(영향 범위 표기) |
  | 벌크 액션 | 행 체크박스 + 선택 수 표기 액션 바, 파괴적 벌크는 확인 | 롱프레스 선택 모드 | 필터 결과 전체 선택 + 확인 |
  | 폼 검증·제출 | 제출 시 검증, 에러난 필드는 blur 재검증, 에러는 필드 하단 인라인 | 필드별 즉시 검증 | admin과 동일 |
  | 피드백 | 성공=토스트(3~4s), 검증 실패=필드 인라인, 그 외 실패=원인 담은 토스트/배너 | 하단 스낵바 | 인라인 배너 |
  | 낙관적 업데이트 | 되돌리기 쉬운 토글류만 | 좋아요·팔로우 등 넓게 | 지양(정합성 우선) |
  | 로딩 | 최초·전체=스켈레톤, 부분 갱신=영역/버튼 인라인 스피너, 300ms↓ 예상이면 생략 | 스켈레톤 + 당겨서 새로고침 | 차트·표별 스켈레톤 |
  | 내비게이션 | 미저장 변경 시 이탈 경고, 모달은 ESC·바깥클릭 닫기(미저장이면 확인), 취소=변경 폐기 | 뒤로 제스처, 스텝 이탈 경고 | admin과 동일 |

  세 성격 어디에도 안 맞으면 기본(admin) 열에서 출발해 무엇을 왜 바꿨는지 근거로 남긴다.
- **컴포넌트형 웹이면(3단계에서 Storybook을 넣은 경우) 규약을 Storybook 정본 story로 실현한다 — story는 필수.** markdown 결정 표는 그대로 규칙·근거·임계의 정본으로 두고, 그 위에 각 규약을 담는 정본 컴포넌트마다 정본 story를 둔다(부류 → 정본 컴포넌트 → 그 story가 보여줄 규약 동작).
- **play-function 인터랙션 테스트는 선택이다 — 사용자·프로젝트가 정한다.** CI로 규약을 강제하고 싶으면 채택해 각 story에 인터랙션 테스트(play 함수 또는 동급의 컴포넌트 인터랙션 테스트)를 붙이고(예: 삭제 story는 삭제 클릭 → 확인 다이얼로그 노출을 assert), 원치 않으면 story를 비주얼·참조 정본으로만 둔다. **이 선택을 인터랙션 패턴 절 머리에 한 줄로 기록한다**(예: `인터랙션 테스트: 채택` / `미채택`) — build·gap이 이 값을 읽는다. RFP·사용자 지시에 신호가 없으면 미채택을 기본으로 두고 완료 보고에서 채택 여부를 물을 수 있게 남긴다.
- **단 setup 시점엔 코드가 없으므로 story를 만들지 않는다** — design-guide에는 "어떤 정본 story가 무엇을 보여줄지(+테스트 채택 시 무엇을 assert할지)" 목록만 선언한다. 실제 story·(채택 시)테스트 부트스트랩은 `build`가 첫 UI를 만들 때 한다. 서버 렌더 템플릿·비웹이면 이 선언을 생략하고 결정 표까지만 둔다.
- **이미 화면이 깔린 기존 저장소(brownfield)면 규약을 위에서 아래로 박지 말고 reconcile한다.** baseline은 빈 저장소를 전제로 한 기본값이므로, 현행 앱에 그대로 씌우면 잘 돌던 established 패턴까지 전부 위반으로 만든다. 먼저 현행 각 화면이 부류별로 실제 뭘 하는지 조사하고(코드 조사는 `gap`에 위임 가능), 이미 일관되게 자리잡은 합리적 패턴은 그것을 규약으로 **추인**한다 — baseline과 다르다는 이유만으로 뒤집지 않는다. 나머지는 baseline/추인값을 정본으로 삼아 어긋난 화면을 divergence로 표시한다. design-guide가 이미 있으면 다른 절은 건드리지 말고 인터랙션 패턴 절만 additive로 더한다. 확정한 규약 대비 divergence를 실제 이슈로 만드는 것은 `gap`이 한다 — 6단계는 규약을 확정할 뿐이다.
- (선택) 메뉴·라우트가 복잡하면 `docs/ia.md`(사이트맵 / 메뉴 정의 / 역할별 진입 / 라우트 구조)도 생성한다.

### 7. gap 분석 (fresh-eye subagent)

- Agent 툴로 subagent 1회 dispatch. 프롬프트: "RFP와 PRD를 fresh eye로 읽고, RFP 요구 중 PRD가 누락·모호·상충하는 항목만 목록화하라. 각 항목에 RFP 근거 위치와 제안 보강안을 붙여라. 구현 얘기는 하지 마라."
- 결과를 받아 PRD를 보강한다(누락 요구 추가, 미확정 이슈를 `Q` 항목/결정 이력에 반영).

### 8. CLAUDE.md / README.md 생성

- **이 스킬 디렉터리의** `templates/CLAUDE.md.template`, `templates/README.md.template`을 Read로 읽는다.
  경로는 스킬 파일 기준이지 대상 프로젝트 cwd 기준이 아니다 — 이 스킬은 대상 프로젝트에서 실행되므로
  `./templates/…`로 읽으려 하면 실패한다.
- 공유 baseline은 그대로 두고 `{{…}}` 슬롯을 채운다:
  - `{{PROJECT_TITLE}}`·`{{PROJECT_ONELINE}}`·`{{PROJECT_INTRO}}` ← RFP/PRD의 프로젝트명과 한 줄 소개, 과업 배경.
  - `{{TECH_STACK}}`·`{{COMMANDS}}`·`{{GETTING_STARTED}}` ← 3단계 스택 결정. 예시 프로젝트 값을 그대로 박지 않는다.
  - `{{ARCHITECTURE_PROJECT_NOTES}}` ← PRD 데이터 모델(6장) + 채택 스택으로 실제 디렉터리 경로·모듈별 책임을 도출해 채운다(CLAUDE.md 템플릿의 레이어 baseline 불릿 **아래에** 덧붙인다).
  - `{{PROJECT_STRUCTURE}}` ← README `## 구성`에 주요 디렉터리 한 줄 설명으로 채운다(여긴 baseline 불릿이 없다).
  - `{{IMPLEMENTATION_PROJECT_STANDARDS}}` ← PRD 비기능 요구(5장)·데이터 저장·인증·도메인 규칙 등 프로젝트 고유 기준.
  - `{{ISSUE_BOARD_TARGET}}` ← org/보드/마일스톤. 미정이면 사용자에게 확인.
  - `{{DOMAIN_GLOSSARY}}` ← PRD/RFP 도메인 용어.
  - `{{DOC_LINKS_SENTENCE}}`·`{{DOC_LIST}}`·`{{DOC_ROUTING_TABLE}}` ← 9단계에서 **실제 생성된 문서만으로** 채운다.
  - `{{RFP_URL}}` ← RFP 문서 경로. RFP가 파일로 없으면 그 줄을 지운다.
- **완료 조건: 생성된 CLAUDE.md·README.md에 `{{`가 하나도 남아 있으면 안 된다.** 8단계를 끝내기 전에
  두 파일을 grep해서 확인한다. 채울 값이 없는 슬롯은 빈칸으로 두지 말고 **그 줄을 제거한다.**
- 공유 baseline 불릿(Clean Architecture 원칙 / God Object 방지 / 개발 원칙, 그리고 이슈 관리·Architecture·구현 기준의 baseline 불릿)은 템플릿 그대로 유지하고, `<!-- setup: … -->` 주석은 채운 뒤 지운다.
