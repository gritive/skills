# project prd-to-issue

`/project prd-to-issue` — PRD를 에픽으로 분해해 의존성 순서로 GitHub 이슈를 만든다.

## 절차

### 1. PRD 읽기

- `docs/prd.md`를 Read. 없으면 사용자에게 위치를 묻는다.

### 2. 프로젝트 규칙 로드 (하드코딩 금지)

- 대상 `CLAUDE.md`의 "이슈 관리" 섹션을 읽어 org/보드/마일스톤과 연결 방식을 파악한다.
  - 예: `gh issue create ... --project "<보드명>"` 또는 생성 직후 `gh project item-add <번호> --owner <org> --url <url>`.
- 규칙이 없으면 사용자에게 묻는다. 특정 org/보드 이름을 스킬에 박지 않는다.

### 3. 기존 이슈 컨벤션 확인

- `gh issue list --state all`로 이미 만들어진 이슈가 있는지 본다.
- 있으면 대표 이슈 2~3개 본문을 `gh issue view <n>`으로 열어 **확립된 컨벤션**(제목 접두 분류, 본문 섹션 구조, 의존 표현 방식, 보드 연결)을 그대로 답습한다. 추측하지 않는다.

### 4. 에픽 분해 + 기존 분해와 대조 (DRY)

- 기능 요구(PRD 3장)와 기반 작업(스키마·인증·앱 셸 등)을 에픽으로 묶는다.
- **이미 존재하는 이슈와 대조한다.** 같은 PRD를 이미 분해한 이슈가 있으면 중복 생성하지 말고 갭(누락 에픽, 분할 후보)만 추가한다.
- 에픽 간 의존을 위상정렬한다. 기반(셋업 → 스키마 → 인증 → 셸)이 기능 에픽의 선행이다.

### 4.5. Hollow 이슈 점검 — 생산자↔소비자 짝맞춤

분해한 에픽·이슈 전체를 한눈에 놓고, **무언가를 관리·생산하는 이슈마다 그 산출물을 실제로 쓰는 소비처가 백로그(또는 기존 구현)에 있는지** 확인한다. 관리 기능만 있고 소비처가 없는 이슈는 **hollow**다 — 아무 화면도 읽지 않는 데이터를 쓰기만 하는 관리자 CRUD, 어디에도 표시되지 않는 엔티티, 아무 동작도 바꾸지 않는 설정. 관리 기능이 있는데 소비처가 없으면 그 관리 대상은 죽은 데이터다.

- **생산자 신호**: 엔티티 X의 생성·수정·삭제·관리자 화면, X에 대한 설정·구성 토글, 데이터를 수집·집계·산출하는 기능, 값을 반환하는 API/서비스.
- **소비처 신호**: X를 표시·조회하는 화면/목록/상세, X를 입력으로 쓰는 사용자 흐름, 설정값을 실제로 읽어 동작을 바꾸는 경로, 그 API를 호출하는 클라이언트·다른 서비스.
- **정당한 write-only 예외(hollow가 아니다)**: 소비 주체가 저장소 밖인 것 — 감사 로그·이벤트 기록, 데이터 내보내기·웹훅 발신처럼 **외부 시스템·운영자가 소비**하는 경우. 이때는 이슈 본문에 소비 주체를 명시한다.

짝이 없는 생산자를 발견하면:

- **PRD가 소비처를 함의하면** 누락된 소비 이슈를 분해에 추가한다(관리 이슈의 소비 짝). 위상정렬에서 생산자 뒤에 온다 — 관리 이슈의 `## 의존`에 `선행: <소비 이슈>`가 아니라, 소비 이슈가 생산자를 `선행:`으로 참조한다.
- **PRD가 소비처에 대해 침묵하면 이슈를 지어내지 않는다.** 이건 PRD의 gap일 수 있으므로 **완료 보고에 "생산자 <이슈명>에 소비처 없음(PRD 미언급)"으로 남기고 사용자에게 확인받는다.** 관리 기능이 의도적으로 admin 전용·write-only인지, 아니면 PRD가 소비 화면을 빠뜨린 것인지는 사용자만 안다 — 추측해서 화면 이슈를 만들지도, 조용히 넘기지도 않는다.
- 이 점검은 `gap`의 "구현됐지만 UI 미노출"과 층이 다르다: `gap`은 이미 구현된 코드를 fresh eye로 보고, 여기서는 **아직 만들지 않은 이슈 집합**에서 소비처 없는 생산자를 미리 잡는다. `build`는 구현 직전 게이트(8단계)에서 다시 한 번 잡는다.

### 5. 이슈 본문 (기존 컨벤션 답습 — 3단계에서 확인한 형식)

- 확인된 형식이 없을 때의 기본 형태:
  - 제목: `[분류] 요약` (예: `[기반]` / `[기능]`)
  - 본문 섹션: `## 목적` → `## 범위`(`- [ ]` 체크박스) → `## 참조` → `## 완료 기준` → `## 의존`
  - 에픽 이슈의 `## 범위`는 하위 작업을 체크박스로 나열한다. 하위 작업을 독립 이슈로 쪼갤 때는 그 이슈를 에픽의 sub-issue로 연결하고 대응 체크박스에서 `#N`으로 참조한다. 하위 이슈가 닫히면 `build`가 이 체크박스를 `- [x]`로 갱신한다.
  - 의존 표현: `## 의존`에 산문형 — `선행: <이슈명 또는 #N>` / `부모: #N`. GitHub native `blocked-by`가 리포에서 쓰이면 그쪽을 따른다.

### 6. 위상정렬 순서로 생성

- 선행 이슈를 먼저 만들어 번호를 받고, 뒤 이슈의 `## 의존`에서 `#N`으로 참조한다.
- 각 생성 직후 2단계의 규칙대로 보드에 연결한다.

## 완료 보고

- 생성한 이슈 번호·제목·의존 관계를 표로 요약한다. 중복이라 생성하지 않은 항목도 명시한다.
- **Hollow 점검 결과**(4.5단계): 소비 짝을 새로 추가한 관리 이슈, 그리고 **소비처가 없는데 PRD가 침묵해 사용자 확인이 필요한 생산자**를 별도로 나열한다. 하나도 없으면 "hollow 이슈 없음"으로 명시한다.
