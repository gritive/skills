# subagent 모델 라우팅

`project` 스킬의 모든 subagent dispatch에 적용한다. 특정 공급자·모델명·버전을 이 문서에 고정하지 않는다.
모델 선택은 매 dispatch마다 오케스트레이터가 현재 작업과 호스트 기능을 근거로 수행한다.

## 선택 절차

1. 현재 호스트의 subagent 생성 도구 스키마와 지원 모델을 확인한다. 다른 호스트의 도구명·모델명·옵션을
   추정하지 않는다.
2. 작업의 코드량이 아니라 **판단 난이도**를 평가한다: 요구사항 명확성, 영향 범위, 실패 위험, 필요한
   인과 추론, 예상 탐색량, 검증 난이도.
3. 작업을 안정적으로 끝낼 수 있는 모델 중 비용·지연이 가장 낮은 것을 선택한다.
4. 호스트가 모델 override를 지원하면 그 필드에 유효한 값을 명시한다. override에 추가 제약이 있으면 함께
   지킨다. 지원하지 않으면 부모 모델을 상속한다.
5. 호스트·환경 설정이 선택을 강제하면 그 값을 따르고 완료 보고에 `model routing overridden`과 원인을 남긴다.

## 판단 기준

- 범위가 좁고 절차·정답·검증이 명확한 탐색, 반복 편집, 자료 수집은 가벼운 모델로 충분하다.
- 일반 구현, 테스트 작성, 원인이 명확한 버그 수정, 보통 수준의 gap 분석은 균형형 모델을 쓴다.
- 요구사항이 모호하거나 아키텍처·보안·데이터 정합성·여러 모듈의 인과관계·적대적 리뷰가 핵심이면 강한
  추론 모델을 쓴다.
- 큰 기계적 변경이라는 이유만으로 강한 모델을 고르지 않는다. 작은 작업도 실패 영향이 크고 판단이 어려우면
  강한 모델을 쓴다.
- 하드 게이트나 되돌리기 어려운 결정을 모델 성능으로 우회하지 않는다. 해당 subcommand의 중단 조건이 모델
  라우팅보다 우선한다.

같은 Phase에서 병렬 dispatch하는 subagent도 작업별로 따로 판단한다. 선택한 모델과 이유를 dispatch 로그에
한 줄로 남긴다. 모델 이름을 생략해 부모 모델을 상속했다면 그 사실도 기록한다.
