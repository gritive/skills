# Review Forever

리뷰 스킬을 감싸서 **고칠 것이 없어질 때까지** 리뷰-수정-검증을 반복하는 루프.

이 스킬 자체는 리뷰를 하지 않는다. **다른 리뷰 스킬을 실행하고, 그 결과를 처리한다.**
무엇을 리뷰할지는 감싼 스킬이 정한다.

## 핵심 개념 — 실행 큐

이 루프의 모든 판정(완료·정체·반복)은 감싼 스킬의 **원시 발견 수**가 아니라 **실행 큐**로 잰다.

```
실행 큐 = 감싼 스킬의 발견 − (범위 밖) − (기각한 오탐) − (사용자가 보류한 것)
```

**원시 발견 수로 재면 루프가 영영 끝나지 않는다.** 감싼 스킬은 패스 간 기억이 없어서, 우리가 고치지
않기로 한 레거시 이슈와 이미 기각한 오탐을 **매 패스 다시 보고한다.** 그것들을 세면 발견 수는 절대
0이 되지 않는다. 루프가 지시를 완벽히 따랐는데도 "수렴 실패"로 끝난다.

루프가 책임지는 것은 **자기가 고치기로 한 것**뿐이다. 그러니 그것만 센다.

## 호출 이름 — 반드시 `gritive:` 접두사를 쓴다

**이 스킬은 `/gritive:review-forever`다.** 접두사 없는 `/review-forever`는 **다른 스킬**이다 —
user space(`~/.claude/skills/review-forever/`)에 같은 이름의 원본이 있고, 그쪽에는 아래의 수렴
안전장치가 **하나도 없다**. 문서·안내·자기 참조에서 항상 접두사를 붙인다.

**접두사는 슬래시 호출만 방어한다.** 이 스킬과 원본은 자연어 트리거("클린될 때까지 리뷰", "fix every
finding")가 거의 같아서, 사용자가 자연어로 요청하면 라우터가 원본을 고를 수 있다. 그때 이 문서는
로드조차 되지 않으므로 여기 적힌 안전장치는 걸리지 않는다. 루프를 확실히 쓰려면 슬래시로 부른다.

## 다른 리뷰 스킬과의 차이 — 이 스킬은 코드를 고친다

리뷰어(`codebase-review`의 `reviewers/*.md`)는 읽기 전용이다. 발견 사항만 보고한다.
`review-forever`는 그 발견을 **실제로 고친다.** 그것이 이 스킬의 존재 이유다.
**에이전트가 찾고, 루프가 고친다.**

패스별 리포트·로그는 대화로 출력한다.

## 인자

```
/gritive:review-forever                          → gstack review 스킬 (기본)
/gritive:review-forever code-review              → Claude Code 내장 code-review
/gritive:review-forever codebase-review          → gritive의 도메인별 리뷰어
/gritive:review-forever codebase-review --domain security   → 감싼 스킬의 인자를 그대로 전달
/gritive:review-forever plan-eng-review          → 다른 플러그인·유저 스킬도 감쌀 수 있다
/gritive:review-forever --max-passes 3           → 첫 인자가 플래그면 기본 스킬 + 플래그로 해석
```

**첫 인자가 `--`로 시작하지 않으면 리뷰 스킬 이름이다.** `--`로 시작하면 스킬 이름이 생략된 것이므로
기본 스킬을 쓴다. 스킬 이름 뒤의 나머지 인자는 **감싼 스킬에 그대로 넘긴다** — 루프가 해석하지 않는다.
단 `--max-passes N`은 루프가 가져간다 (감싼 스킬에 넘기지 않는다 — 모르는 플래그를 받으면 중단하는
스킬이 있다).

### 기본 스킬은 gstack의 `review`다

인자가 없으면 `review`를 호출한다. **이 이름은 Claude Code 내장 `review`가 아니라 gstack의 `review`로
해석된다** — personal 스킬이 bundled 스킬을 덮어쓰기 때문이다. 이는 의도된 것이다. gstack `review`는
작업 중인 diff(워킹트리 포함)를 보므로 이 루프에 맞는다.

내장 스킬을 명시적으로 쓰려면 이름을 직접 준다 — `code-review`(작업 중인 diff).

### 스킬 이름 해석

- **gritive 플러그인 스킬** — `gritive:` 접두사를 붙여 호출한다. 사용자가 `codebase-review`로 써도
  호출은 `gritive:codebase-review`다
- **다른 플러그인 스킬** — 그 플러그인의 접두사가 필요하다. 접두사를 모르면 **추측하지 말고**
  사용 가능한 스킬 목록에서 확인한다. 못 찾으면 중단한다
- **내장·유저 스킬** — 접두사가 없다

인자로 받은 이름이 리뷰/평가 워크플로가 아니거나 존재하지 않으면 **중단하고 그 사실을 알린다.**

### 감쌀 수 없는 것 — `full` 스캔

`codebase-review full`처럼 **변경 범위가 없는 전체 스캔은 루프로 감싸지 않는다.** 실행 큐는 "이 변경이
유발한 것"과 "원래 있던 것"을 가르는 데서 나오는데, `full`에는 그 경계가 없다. 전부 범위 밖이거나 전부
범위 안이 되어 루프가 코드베이스 전체를 고치려 들거나 아무것도 안 고친다.

사용자가 `full`을 주면 **중단하고 안내한다**: 전체 스캔은 `/gritive:codebase-review full`로 한 번 돌리고,
그 리포트에서 고칠 것을 정한 뒤, 그 변경분에 대해 이 루프를 돌리면 된다.

## Workflow

### Phase 1: 대상·완료 조건·수정 반영 방식을 정한다

시작 전에 명시하고 시작한다:

- **감싼 리뷰 스킬** — 해석된 최종 이름으로
- **리뷰 대상** — 브랜치/PR/diff/경로
- **완료 조건** — 실행 큐가 빌 때
- **패스 상한** — 기본 5

**감싼 스킬이 비용 확인을 요구하면 루프 전체에 대해 한 번만 받는다.** 매 패스 다시 묻지 않는다 —
사용자는 루프를 승인한 것이지 패스 하나를 승인한 게 아니다. 승인 범위(패스 상한까지)를 분명히 말한다.

#### 루프의 수정이 다음 패스에 보이게 하는 법 — 여기서 정한다

**감싼 스킬이 무엇을 리뷰 대상으로 잡는지에 따라 갈린다.** 이건 취향이 아니라 **사용자 작업이
커밋돼 있느냐**로 결정된다. 잘못 고르면 패스 1에서 죽는다.

**먼저 사용자 작업이 어디에 있는지 본다. 두 신호가 모두 필요하다:**

```bash
git status --porcelain              # 워킹트리가 더러운가
git rev-list --count {base}..HEAD   # 브랜치에 커밋이 쌓였는가
```

**`git status --porcelain` 하나로는 판정할 수 없다.** 그것은 워킹트리가 더러운지만 말하고 브랜치에
커밋이 있는지는 말하지 않는다 — "전부 미커밋"과 "섞임"이 **똑같이 비어있지 않은 출력**을 낸다.
두 신호를 함께 봐야 셋이 갈린다.

| porcelain | 커밋 수 | 사용자 작업 상태                   | 감싼 스킬                                | 루프 수정의 반영                                                                               |
| --------- | ------- | ---------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 빔        | > 0     | **전부 커밋됨** (일반적인 PR 상황) | `codebase-review` (기본 `{base}...HEAD`) | **패스마다 커밋해야 한다.** 커밋 기반 diff라 미커밋 수정은 다음 패스의 파일 목록에 안 들어온다 |
| 안 빔     | 0       | **전부 미커밋** (워킹트리 작업 중) | `codebase-review --working`              | 자동으로 보인다. 루프 수정도 미커밋이므로 같이 잡힌다                                          |
| 안 빔     | > 0     | **섞임** (커밋 + 미커밋)           | **어느 쪽도 안 된다**                    | **중단.** 아래 참조                                                                            |
| —         | —       | 아무거나                           | gstack `review`, 내장 `code-review`      | 자동으로 보인다. **워킹트리를 보는 스킬이라 이 문제가 없다**                                   |

**`--working`은 "커밋을 남기기 싫을 때"의 대안이 아니다.** 작업이 이미 커밋된 브랜치에서 `--working`을
고르면 미커밋 변경분이 0개라 감싼 스킬이 "리뷰할 변경분 없음"으로 중단한다 — 한 줄도 리뷰되지 않는다.
두 방식은 **전제조건이 배타적**이다.

**섞인 상태가 가장 위험하다.** `codebase-review`에는 커밋과 미커밋을 **함께** 보는 모드가 없다.
그래서 어느 쪽을 골라도 사용자 작업의 절반이 리뷰되지 않는데, **감싼 스킬은 중단하지 않는다** —
파일 목록이 비어 있지 않으니 정상적으로 돌고 정상적으로 발견을 낸다. 루프는 본 것만 고치고 큐를 비운
뒤 "완료"를 보고한다. Phase 2의 중단 판별 표는 이걸 잡지 못한다 (그 표는 "감싼 스킬이 멈췄는가"만
보지 "대상의 부분집합만 봤는가"는 보지 않는다). **리뷰되지 않은 코드에 클린을 선언하게 된다.**

그러므로 섞인 상태면 **루프를 시작하지 않는다.** 사용자에게 알리고 정리를 요청한다 — 미커밋 작업을
커밋하거나(→ 전부 커밋됨), stash하거나(→ 그 작업은 이번 리뷰 대상에서 빠진다는 것을 명시). 정리된
뒤에 시작한다. 워킹트리를 보는 스킬(gstack `review`, 내장 `code-review`)을 감쌀 때는 이 문제가 없다.

**패스마다 커밋해야 하는 경우, 먼저 사용자에게 확인받는다.** 통보가 아니라 승인이다 — 루프가 사용자
브랜치에 커밋을 쌓는 일이기 때문이다. 확인받았으면:

- **루프가 편집한 파일만 이름으로 스테이징한다.** `git add -A`나 `git commit -a`를 쓰지 않는다 —
  워킹트리에 남아 있던 사용자의 무관한 작업이 딸려 들어간다
- 커밋 메시지는 `fix: {고친 것}`. 대상 프로젝트의 커밋 메시지 규칙이 있으면 그것을 따른다

**이 질문에는 예외 하나와 강등 경로 하나가 있다.**

- **자율 호출 — 아무것도 묻지 않는다.** 호출자가 프롬프트에 **"자율 루프다"**와 그 지시를 명시했으면
  그것이 사전 승인이다(`project build` 9.5단계가 그렇게 부른다). 그 커맨드를 실행한 것 자체가
  승인이므로 다시 묻는 것은 계약 위반이다. 이때 두 가지가 바뀐다:
  (1) **커밋 승인을 묻지 않고 패스마다 커밋한다.**
  (2) **판단이 필요한 발견도 묻지 않는다** — Phase 3의 "애매하거나 제품 결정이 필요한 발견은 사용자에게
  묻는다"와 Phase 6의 "사용자 결정이 필요한 발견" 중단 조건이 **이때만 보류 처리로 바뀐다.** 큐 밖으로
  빼고 완료 보고에 "판단 필요 — 보류"로 올린다. **추측해서 고치지 않는다**(그건 원래 금지다).
  **호출자가 명시하지 않았으면 이 예외는 없다** — 추측해서 적용하지 않는다.
- **물을 수 없으면 커밋하지 않는다(강등 경로).** subagent로 실행 중이면 `AskUserQuestion`이 없어
  승인을 받을 수 없다. 그때는 **수정을 워킹트리에 남긴 채** 고친 파일 목록과 함께 반환한다.
  커밋 여부는 호출자가 정한다. **승인 없이 커밋하지도, 수정을 되돌리지도 않는다.**

어느 쪽이든 **커밋했는지 워킹트리에 남겼는지를 완료 보고에 명시한다** — 호출자가 push 전에
확인해야 하고, 안 적으면 리뷰 수정이 머지에서 누락된다.

### Phase 2: 리뷰 실행

`Skill` 툴로 감싼 리뷰 스킬을 호출한다. 인자는 사용자가 준 것을 그대로 넘긴다.

**감싼 스킬이 "중단"했는지 "발견 0건"인지 반드시 구분한다.** 이 둘은 똑같이 조용하지만 정반대다:

| 감싼 스킬의 응답                             | 뜻                        | 루프의 처리             |
| -------------------------------------------- | ------------------------- | ----------------------- |
| 리뷰가 돌았고 발견 0건                       | 검사했고 깨끗하다         | **완료** (Phase 6)      |
| **볼 대상이 없어서** 아무것도 안 띄움         | 검사할 코드가 없었다      | **완료** (아래 참조)    |
| "리뷰할 변경분 없음" (대상 파일 자체가 0개)  | 리뷰 범위가 잘못 잡혔다   | **중단.** 클린이 아니다 |
| base branch 탐지 실패, git 명령 실패, 타임아웃 | 리뷰가 못 돌았다          | **중단.** 클린이 아니다 |

**판정은 리뷰어가 낸 상태 줄로 한다 — 리포트 셀의 문자열로 하지 않는다.** `codebase-review`는
Phase 4에서 `REVIEW_STATUS: ran|no-target|aborted`를 낸다. `ran`이면 리뷰가 돈 것이고,
도메인별 대시보드에 `N/A (대상 파일 없음)` 셀이 몇 개 있든 **정상이다** — 그것은 "이 축에는
볼 파일이 없었다"는 사람용 표기이지 미실행 신호가 아니다. **셀 문자열로 판정하면 프론트엔드
파일이 없는 평범한 백엔드 변경마다 루프가 중단한다.**

- `ran` → 발견을 트리아지한다(Phase 3).
- `no-target` → **완료로 친다.** 코드가 안 바뀌었으면(문서·텍스트 전용 diff) 코드 리뷰가 찾을
  것이 없는 게 맞다. 사유를 완료 보고에 그대로 적어 "검사했고 깨끗함"과 구분되게 한다.
- `aborted` → 중단. 사유를 그대로 전하고 루프를 끝낸다.

**상태 줄을 안 내는 리뷰 스킬을 감쌀 때**(gstack `review`, 내장 `code-review` 등)는 위 표의
응답 문구로 판정하되, **애매하면 중단으로 친다.**

**"검사하지 않음"을 "발견 0건"으로 보고하는 것이 이 루프의 최악의 실패다.** 한 줄도 리뷰하지 않고
"클린 달성"을 선언하게 된다. 그래서 `no-target`도 "깨끗함"이 아니라 **"볼 것이 없었음"**으로 보고한다.

### Phase 3: 트리아지 — 여기서 실행 큐가 만들어진다

원시 발견을 셋으로 가른다. **실행 큐에 넣는 것은 첫 번째뿐이다.**

**1. 고친다 (→ 실행 큐).** 구체적인 버그, 회귀, 안전 문제, 누락된 테스트, 명시된 규칙 위반.
심각도 순으로 정렬한다 (CRITICAL → HIGH → MEDIUM → LOW).

**2. 기각한다 (→ 큐 밖).** 소스에서 검증했더니 틀린 발견. 왜 틀렸는지 근거를 남긴다.
**오탐을 달래려고 코드를 바꾸지 않는다** — 이것이 가장 나쁜 실패다.

**3. 보고만 한다 (→ 큐 밖).** 요약·통계·니트픽·선택적 제안. 그리고 **변경 범위 밖의 레거시 이슈.**

범위 밖 판정이 중요하다. `codebase-review`의 `base-diff`는 '변경된 파일' 단위이지 '변경된 라인'
단위가 아니다 — 900줄 파일에서 3줄만 고쳐도 900줄 전체가 리뷰 대상이다. 그래서 **사용자가 손대지도
않은 레거시 코드의 발견이 섞여 들어온다.** 이런 발견은 고치지 않고 별도로 보고한다. 고칠지는 사용자가
정한다. 예외는 그 발견이 이번 변경과 **인과적으로 얽힌** 경우다 (이번 변경이 유발했거나, 이번 변경이
만든 버그의 근본 원인이거나).

이 구분을 지키지 않으면 루프가 무관한 리팩토링으로 번지고, diff가 오염되고, **완료 조건에 영영 닿지
못한다.**

**애매하거나 제품 결정이 필요한 발견은 사용자에게 묻는다.** 추측해서 고치지 않는다.
**자율 호출이면 묻지 말고 보류로 뺀다**(Phase 1의 "자율 호출" 조항).
사용자가 보류를 택하면 큐 밖으로 뺀다.

### Phase 4: 수정

- **가장 작은 변경으로** 문제를 해결한다
- 사용자의 무관한 변경분을 보존한다
- 동작·회귀 위험·누락된 가드에 대한 발견이면 **테스트를 추가하거나 갱신한다**
- **리뷰 코멘트를 고치면서 무관한 리팩토링을 하지 않는다.** 다음 패스의 diff가 오염된다

### Phase 5: 검증

- 건드린 영역에 대해 **가장 좁은 의미 있는 테스트/체크**를 돌린다
- 자동 체크가 없으면 대상을 직접 확인하고 **그렇게 했다고 밝힌다**
- **수정이 깨뜨린 테스트는 다음 패스 전에 해결한다.** 깨진 채로 재리뷰하지 않는다
- Phase 1에서 "패스마다 커밋"을 택했다면 **여기서 커밋한다** (루프가 편집한 파일만 이름으로 스테이징,
  Phase 1에서 정한 접두사로)

### Phase 6: 수렴 판정

**실행 큐가 비면 완료한다.** (감싼 스킬이 여전히 레거시 이슈나 기각한 오탐을 보고하고 있어도 상관없다 —
그것들은 큐에 없다. 완료 보고에서 따로 밝힌다.)

아니면 Phase 2로 돌아간다. 단, 아래 중 하나면 **멈추고 보고한다**:

| 중단 조건                                                           | 이유                                        |
| ------------------------------------------------------------------- | ------------------------------------------- |
| 패스 수가 `--max-passes`(기본 5) 도달                               | 무한 루프 방지                              |
| **실행 큐가 두 패스 연속 줄지 않음** (큐가 비어 있지 않은 상태에서) | 수정이 문제를 해결하지 못하고 옮기고만 있다 |
| **같은 큐 항목이 3회 반복**                                         | 고쳤는데 또 돌아온다 = 수정이 안 먹힌다     |
| 감싼 스킬이 **중단**함 (Phase 2 표 참조)                            | 리뷰가 돌지 않았다. 클린이 아니다           |
| 자격 증명·서비스 부재, 안전하지 않은 프로덕션 접근                  | 진행 불가                                   |
| 사용자 결정이 필요한 발견 (**자율 호출이면 중단이 아니라 보류**)    | 물어봐야 한다 — 자율 호출에서는 보류로 빼고 계속한다 |

**정체 판정은 실행 큐로만 잰다. 큐가 비어 있으면 그것은 정체가 아니라 완료다** — "0이 두 패스 연속
그대로"를 정체로 읽으면 정상 종료를 죽인다. 원시 발견 수로 재도 안 된다: 레거시와 기각 오탐이 매 패스
그대로 다시 보고되므로 항상 "정체"로 보인다.

**"3회 반복"도 큐 항목만 센다.** 큐 밖으로 뺀 것(레거시·기각한 오탐)은 감싼 스킬이 매 패스 다시
보고하므로 **정의상 3패스째에 "3회 반복"이 된다.** 그것까지 세면 큐가 5 → 2 → 1로 잘 줄고 있는데도
중단 조건이 발동한다. 기각이 유지되고 있는 오탐과 범위 밖 레거시는 몇 번을 재보고되든 **신호가 아니다.**
신호인 것은 **고치기로 해서 실제로 고쳤는데 또 돌아온 항목**뿐이다.

**발견의 동일성은 `파일 + 문제의 요지`로 판정한다. 라인 번호와 심각도는 키에서 제외한다** —
코드를 고치면 라인이 밀리고, 부분 수정은 심각도를 낮춘다(CRITICAL → MEDIUM). 둘 중 하나라도 키에
넣으면 같은 발견이 새 발견으로 보여 반복 카운터가 영영 올라가지 않는다.

### 분류를 패스마다 뒤집지 않는다

감싼 스킬은 기억이 없으므로 **큐는 매 패스 재구성된다.** 그런데 정체 판정은 큐 크기의 패스 간
비교다 — 재분류가 흔들리면 **유일한 수렴 지표가 흔들린다.** 아무것도 안 고쳤는데 재분류만으로 큐가
줄어 보이거나(거짓 진행), 레거시 하나가 큐 안으로 들어와 정체로 보인다(거짓 정체).

**한 번 기각·범위 밖으로 분류한 발견은 새 근거가 없는 한 이후 패스에서 재분류하지 않는다.**
분류를 바꿔야 할 근거가 생겼으면 **그 사실과 이유를 패스 요약에 밝힌다.** 조용히 뒤집지 않는다.

**기각 목록과 범위 밖 목록은 매 패스 요약에 다시 싣고, 다음 패스에서 그대로 재사용한다.**
파일로 남기지 않으므로 대화에만 존재하고, 요약에서 빠지면 압축 때 사라진다. 그러면 루프는 앞서
기각한 오탐을 다시 "고치게" 된다 — Phase 3이 가장 경계한 실패다.

**수렴하지 않는 것은 실패가 아니라 신호다.** 큐가 안 줄면 접근이 틀렸다는 뜻이다.
억지로 더 돌리지 말고, 왜 수렴하지 않는지를 보고한다.

## 완료 보고

**실행 큐가 빈 즉시, 다른 작업으로 넘어가기 전에** 대화에 요약을 낸다.
호출한 상위 스킬(feature-pipeline 등)이 이 보고를 삼키게 두지 않는다.

포함할 것:

- 감싼 리뷰 스킬(해석된 최종 이름)과 리뷰 대상
- **마지막 패스의 리뷰 상태 줄을 그대로 올린다** — `codebase-review`를 감쌌으면
  `REVIEW_STATUS: ran|no-target|aborted`를 원문 그대로. **상태 줄을 안 내는 스킬을 감쌌으면
  "상태 줄 없음(감싼 스킬: {이름})"이라고 적는다.** 이 줄을 소비만 하고 안 올리면, 이 루프를 호출한
  게이트(`project build` 9.5)가 "리뷰가 실제로 돌았는지"를 판정할 근거를 잃는다 — 소비자가
  둘(이 루프, 그리고 이 루프의 호출자)이라는 것을 잊지 마라
- **패스 수와 패스별 실행 큐 크기** (예: `큐 5 → 2 → 0`). 원시 발견 수를 함께 적되 **둘을 구분한다**
- 수정한 내용 요약. 패스마다 커밋했다면 그 커밋들
- **실행한 검증 명령과 그 결과** — "통과했다"가 아니라 무엇을 돌려서 무엇이 나왔는지
- **기각한 발견과 근거** (오탐)
- **고치지 않고 보고만 한 발견** (범위 밖 레거시). 사용자가 이걸 보고 다음 작업을 정한다
- **판단이 필요해 보류한 발견** (자율 호출에서만 생긴다) — **심각도와 함께 전부.** 큐에서 뺐다는 것이
  "괜찮다"는 뜻이 아니다. 호출자가 이것을 게이트에서 세므로(`project build`의 "리뷰 게이트" 절),
  안 적으면 판단이 필요한 CRITICAL이 큐 0으로 통과해 그대로 머지된다
- 클린에 도달하지 못했다면 **왜 멈췄는지**와 남은 위험

검증하지 않은 것을 검증했다고 말하지 않는다. 수정했으나 테스트가 없어 확인 못 한 것은 그렇게 밝힌다.
감싼 스킬이 중단해서 끝났다면 **클린이라고 말하지 않는다.**
