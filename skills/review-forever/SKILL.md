# Review Forever

리뷰 스킬을 감싸서 **고칠 것이 없어질 때까지** 리뷰-수정-검증을 반복하는 루프.

**다른 리뷰 스킬을 실행하고 그 결과를 처리한다.** 무엇을 리뷰할지는 감싼 스킬이 정한다.
`리뷰 → 트리아지 → 수정 → 검증 → 재리뷰`를 실행 큐가 빌 때까지 반복한다.

## 핵심 개념 — 실행 큐

이 루프의 모든 판정(완료·정체·반복)은 감싼 스킬의 **원시 발견 수**가 아니라 **실행 큐**로 잰다.

```
실행 큐 = 감싼 스킬의 발견 − (범위 밖) − (기각한 오탐) − (사용자가 보류한 것)
```

**루프가 책임지는 것은 자기가 고치기로 한 것뿐이고, 세는 것도 그것뿐이다.** 감싼 스킬은 패스 간 기억이
없어 레거시 이슈와 이미 기각한 오탐을 매 패스 다시 보고하므로, 원시 발견 수로는 0에 닿지 않는다.

## 인자

감쌀 리뷰 스킬을 첫 인자로 받는다.

```
/gritive:review-forever                          → gstack review 스킬 (기본)
/gritive:review-forever code-review              → Claude Code 내장 code-review
/gritive:review-forever codebase-review          → gritive의 도메인별 리뷰어
/gritive:review-forever codebase-review --domain security   → 감싼 스킬의 인자를 그대로 전달
/gritive:review-forever plan-eng-review          → 다른 플러그인·유저 스킬도 감쌀 수 있다
/gritive:review-forever --max-passes 3           → 첫 인자가 플래그면 기본 스킬 + 플래그로 해석
```

**첫 인자가 `--`로 시작하지 않으면 리뷰 스킬 이름이다.** `--`로 시작하면 스킬 이름이 생략된 것이므로
기본 스킬을 쓴다. 스킬 이름 뒤의 나머지 인자는 **감싼 스킬에 그대로 넘긴다** — 루프가 해석하지 않는다.
단 `--max-passes N`은 루프가 가져간다 (감싼 스킬에 넘기지 않는다 — 모르는 플래그를 받으면 중단하는
스킬이 있다).

### 기본 스킬은 gstack의 `review`다

인자가 없으면 `review`를 호출한다. **이 이름은 Claude Code 내장 `review`가 아니라 gstack의 `review`로
해석된다** — personal 스킬이 bundled 스킬을 덮어쓰기 때문이다. 이는 의도된 것이다. gstack `review`는
작업 중인 diff(워킹트리 포함)를 보므로 이 루프에 맞는다.

내장 스킬을 명시적으로 쓰려면 이름을 직접 준다 — `code-review`(작업 중인 diff).

### 스킬 이름 해석

- **이 스킬 자신** — `/gritive:review-forever`다. 접두사 없는 `/review-forever`는 user space
  (`~/.claude/skills/review-forever/`)의 **다른 스킬**이며 아래 수렴 안전장치가 없다.
  문서·안내·자기 참조에서 항상 접두사를 붙인다
- **gritive 플러그인 스킬** — `gritive:` 접두사를 붙여 호출한다. 사용자가 `codebase-review`로 써도
  호출은 `gritive:codebase-review`다
- **다른 플러그인 스킬** — 그 플러그인의 접두사가 필요하다. 접두사는 **사용 가능한 스킬 목록에서
  확인한 것만 쓴다.** 못 찾으면 중단한다
- **내장·유저 스킬** — 접두사가 없다

인자로 받은 이름이 리뷰/평가 워크플로가 아니거나 존재하지 않으면 **중단하고 그 사실을 알린다.**

### 감쌀 수 없는 것 — `full` 스캔

루프에는 base 대비 변경 범위가 필요하다. 실행 큐가 "이 변경이 유발한 것"과 "원래 있던 것"의 경계에서
나오기 때문이다. `codebase-review full`처럼 그 경계가 없는 전체 스캔을 주면 **중단하고 안내한다**:
전체 스캔은 `/gritive:codebase-review full`로 한 번 돌리고, 그 리포트에서 고칠 것을 정한 뒤,
그 변경분에 대해 이 루프를 돌리면 된다.

## Workflow

### Phase 1: 대상·완료 조건·수정 반영 방식을 정한다

시작 전에 명시하고 시작한다:

- **감싼 리뷰 스킬** — 해석된 최종 이름으로
- **리뷰 대상** — 브랜치/PR/diff/경로
- **완료 조건** — 실행 큐가 빌 때
- **패스 상한** — 기본 5

**감싼 스킬이 비용 확인을 요구하면 루프 전체에 대해 한 번만 받는다** — 사용자는 루프를 승인한 것이지
패스 하나를 승인한 게 아니다. 승인 범위(패스 상한까지)를 분명히 말한다.

#### 루프의 수정이 다음 패스에 보이게 하는 법 — 여기서 정한다

**사용자 작업이 어디에 있는지로 결정된다. 두 신호를 함께 본다:**

```bash
git status --porcelain              # 워킹트리가 더러운가
git rev-list --count {base}..HEAD   # 브랜치에 커밋이 쌓였는가
```

아래 표가 모든 경우를 덮는다. 해당 행의 조합을 그대로 택한다.

| porcelain | 커밋 수 | 사용자 작업 상태                   | 감싼 스킬                                | 루프 수정의 반영                                                                               |
| --------- | ------- | ---------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 빔        | > 0     | **전부 커밋됨** (일반적인 PR 상황) | `codebase-review` (기본 `{base}...HEAD`) | **패스마다 커밋해야 한다.** 커밋 기반 diff라 미커밋 수정은 다음 패스의 파일 목록에 안 들어온다 |
| 안 빔     | 0       | **전부 미커밋** (워킹트리 작업 중) | `codebase-review --working`              | 자동으로 보인다. 루프 수정도 미커밋이므로 같이 잡힌다                                          |
| 안 빔     | > 0     | **섞임** (커밋 + 미커밋)           | 없음                                     | **루프를 시작하지 않는다.** 사용자에게 정리를 요청한다 — 커밋하거나(→ 1행), stash하거나(→ 그 작업은 이번 대상에서 빠진다고 명시) |
| —         | —       | 아무거나                           | gstack `review`, 내장 `code-review`      | 자동으로 보인다. 워킹트리를 보는 스킬이라 이 판별이 필요 없다                                  |

섞인 상태를 시작하지 않는 이유: `codebase-review`에는 커밋과 미커밋을 함께 보는 모드가 없어 어느 쪽을
골라도 사용자 작업의 절반만 리뷰되는데, 파일 목록이 비어 있지 않으므로 감싼 스킬은 정상적으로 돌고
Phase 2의 상태 판정도 이를 잡지 못한다 — 리뷰되지 않은 코드에 클린을 선언하게 된다.

**패스마다 커밋해야 하는 경우, 먼저 사용자에게 승인받는다** — 루프가 사용자 브랜치에 커밋을 쌓는
일이기 때문이다. 승인받았으면:

- **루프가 편집한 파일만 경로로 스테이징한다.** 전체 스테이징은 워킹트리에 남은 사용자의
  무관한 작업을 딸려 넣는다
- 커밋 메시지는 `fix: {고친 것}`. 대상 프로젝트의 커밋 메시지 규칙이 있으면 그것을 따른다

**자율 루프로 호출됐거나 `AskUserQuestion`이 없는 subagent로 실행 중이면
`references/autonomous-invocation.md`를 읽고 그 조항을 따른다.** 이 문서는 Phase 3의 "묻는다"와
Phase 6의 "사용자 결정이 필요한 발견"도 함께 규정한다.

### Phase 2: 리뷰 실행

`Skill` 툴로 감싼 리뷰 스킬을 호출한다. 인자는 사용자가 준 것을 그대로 넘긴다.

**감싼 스킬이 "중단"했는지 "발견 0건"인지 반드시 구분한다.** 판정 경로는 감싼 스킬이 상태 줄을
내느냐로 갈린다.

**상태 줄을 내는 스킬** (`codebase-review` 등) — 상태 줄 하나로만 판정한다. 값의 정의와 산출
위치는 `../codebase-review/SKILL.md`에 있다. 루프의 처리는:

- `ran` → 발견을 트리아지한다(Phase 3).
- `no-target` → **완료로 친다.** 코드가 안 바뀌었으면(문서·텍스트 전용 diff) 코드 리뷰가 찾을
  것이 없는 게 맞다. 보고에는 `no-target`을 그대로 적어 "검사했고 깨끗함"과 구분한다.
- `aborted` → 중단. 사유를 그대로 전하고 루프를 끝낸다.

도메인별 대시보드에 `N/A (대상 파일 없음)` 셀이 몇 개 있든 **정상이다** — 그것은 "이 축에는 볼 파일이
없었다"는 사람용 표기이지 미실행 신호가 아니다. 셀 문자열이 아니라 상태 줄로 판정하면 프론트엔드
파일이 없는 평범한 백엔드 변경도 그대로 진행된다.

**상태 줄을 안 내는 스킬** (gstack `review`, 내장 `code-review` 등) — 응답 문구로 판정하되,
**애매하면 중단으로 친다.**

| 감싼 스킬의 응답                             | 뜻                        | 루프의 처리             |
| -------------------------------------------- | ------------------------- | ----------------------- |
| 리뷰가 돌았고 발견 0건                       | 검사했고 깨끗하다         | **완료** (Phase 6)      |
| **볼 대상이 없어서** 아무것도 안 띄움        | 검사할 코드가 없었다      | **완료.** 그 사유를 보고에 적는다 |
| "리뷰할 변경분 없음" (대상 파일 자체가 0개)  | 리뷰 범위가 잘못 잡혔다   | **중단.** 클린이 아니다 |
| base branch 탐지 실패, git 명령 실패, 타임아웃 | 리뷰가 못 돌았다        | **중단.** 클린이 아니다 |

### Phase 3: 트리아지 — 여기서 실행 큐가 만들어진다

원시 발견을 셋으로 가른다. **실행 큐에 넣는 것은 첫 번째뿐이다.**

**1. 고친다 (→ 실행 큐).** 구체적인 버그, 회귀, 안전 문제, 누락된 테스트, 명시된 규칙 위반.
**모든 심각도가 큐에 든다 — MEDIUM·LOW도 포함이다.** 이 루프의 완료 조건은 "클린"이고, 심각도를
큐의 입구로 쓰면 그 정의가 깨진다.

**고치는 순서는 CRITICAL → HIGH → 보안 → MEDIUM → LOW다.** 패스 상한이나 사용자 중단으로 끝날 수
있으므로 **순서가 곧 무엇이 살아남는가**다. 그리고 파일이 아직 흔들리는 중에 네이밍·주석을 먼저
다듬으면 그 위에 CRITICAL 수정이 얹혀 그 작업이 무의미해진다.

**심각도는 발견의 성질로만 매긴다** — 고치기 싫은 발견을 LOW로 부르면 그것이 패스 예산 밖으로
밀어내는 방법이 된다.

**2. 기각한다 (→ 큐 밖).** 소스에서 검증했더니 틀린 발견. 왜 틀렸는지 근거를 남기고
**코드는 그대로 둔다.**

**3. 보고만 한다 (→ 큐 밖).** 요약·통계·선택적 제안, 그리고 **변경 범위 밖의 레거시 이슈.**

리포트의 `미검증 관찰` 절은 셋 중 어디도 아니다. **클린을 선언하기 전에 그 절의 각 관찰에 대해
근거 인용을 한 번 다시 시도한다** — 인용에 성공하면 1·2로 가르고, 또 실패하면 그대로 남겨
완료 보고에 전문으로 싣는다. 인용이 어렵다는 이유로 발견이 조용히 사라지는 것을 막는 자리다.

범위 밖 판정이 중요하다. `codebase-review`의 `base-diff`는 '변경된 파일' 단위이지 '변경된 라인'
단위가 아니다 — 900줄 파일에서 3줄만 고쳐도 900줄 전체가 리뷰 대상이다. 그래서 **사용자가 손대지도
않은 레거시 코드의 발견이 섞여 들어온다.** 이런 발견은 고치지 않고 별도로 보고한다. 고칠지는 사용자가
정한다. 예외는 그 발견이 이번 변경과 **인과적으로 얽힌** 경우다 (이번 변경이 유발했거나, 이번 변경이
만든 버그의 근본 원인이거나).

이 구분을 지켜야 루프가 대상 범위 안에 머물고 diff가 깨끗하게 유지되며 완료 조건에 닿는다.

**애매하거나 제품 결정이 필요한 발견은 사용자에게 묻고, 답을 받은 뒤에 고친다.**
사용자가 보류를 택하면 큐 밖으로 뺀다.
(자율 호출·subagent 실행은 `references/autonomous-invocation.md`를 따른다.)

**단, 묻거나 보류하기 전에 답이 이미 있는지 본다.** 코드 주석·프로젝트 CLAUDE.md·design-guide·PRD·
인접 구현 중 하나가 그 결정을 이미 적고 있으면 **그것이 답이고 보류가 아니다.** 근거 위치(파일·절)를
밝히고 정상 트리아지한다. 근거 위치를 밝힐 수 있을 때만 이 경로를 쓰고, 못 밝히면 보류한다.
**미결정 항목이 든 결정 이슈로 넘기는 것은 기준 문서 어디에도 답이 없을 때뿐이다.**

### Phase 4: 수정

- **가장 작은 변경으로** 문제를 해결한다 — 단 덧붙이는 모양이면 아래를 먼저 본다
- 사용자의 무관한 변경분을 보존한다
- 동작·회귀 위험·누락된 가드에 대한 발견이면 **테스트를 추가하거나 갱신한다**
- **한 패스의 diff는 그 패스가 고치기로 한 발견에 한정한다.** 무관한 리팩토링이 섞이면 다음 패스의 diff가 오염된다

#### 덧붙여 고치기 전에 되돌리기를 먼저 본다

가드·특수 케이스 분기·문자열 매핑·타입 캐스트·새 자료구조처럼 **코드를 더해서** 고치고 있으면,
그 발견을 만든 것이 **앞 패스가 얹은 메커니즘**은 아닌지 먼저 본다. 맞으면 걷어내는 쪽을 우선한다.

**"가장 작은 변경"과 충돌하면 이쪽이 이긴다.** 가드 하나 얹는 것이 거의 항상 diff는 더 작고,
그래서 이 규칙이 없으면 패스마다 메커니즘이 하나씩 쌓인다.

**같은 파일이 두 패스 연속 커지고 있으면 그 자체가 신호다** — 앞 패스를 되돌린 자리에서 다시 본다.

### Phase 5: 검증

- 건드린 영역에 대해 **가장 좁은 의미 있는 테스트/체크**를 돌린다
- 자동 체크가 없으면 대상을 직접 확인하고 **그렇게 했다고 밝힌다**
- **수정이 깨뜨린 테스트는 다음 패스 전에 해결한다.** 테스트가 초록일 때만 재리뷰로 간다
- Phase 1에서 "패스마다 커밋"을 택했다면 **여기서 커밋한다** (루프가 편집한 파일만 이름으로 스테이징,
  Phase 1에서 정한 접두사로)

### Phase 6: 수렴 판정

**실행 큐가 비면 완료한다.** (감싼 스킬이 여전히 레거시 이슈나 기각한 오탐을 보고하고
있어도 상관없다 — 그것들은 큐에 없다. 완료 보고에서 따로 밝힌다.)

아니면 Phase 2로 돌아간다. 단, 아래 중 하나면 **멈추고 보고한다**:

| 중단 조건                                                           | 이유                                        |
| ------------------------------------------------------------------- | ------------------------------------------- |
| 패스 수가 `--max-passes`(기본 5) 도달                               | 무한 루프 방지                              |
| **실행 큐가 두 패스 연속 줄지 않음** (큐가 비어 있지 않은 상태에서) | 수정이 문제를 해결하지 못하고 옮기고만 있다 |
| **같은 큐 항목이 3회 반복**                                         | 고쳤는데 또 돌아온다 = 수정이 안 먹힌다     |
| 감싼 스킬이 **중단**함 (Phase 2 참조)                               | 리뷰가 돌지 않았다. 클린이 아니다           |
| 자격 증명·서비스 부재, 안전하지 않은 프로덕션 접근                  | 진행 불가                                   |
| 사용자 결정이 필요한 발견                                           | 물어봐야 한다                               |

마지막 행은 자율 호출·subagent 실행에서 보류로 바뀐다 — `references/autonomous-invocation.md`.

정체·반복 판정은 "핵심 개념 — 실행 큐"가 정의한 **실행 큐 항목만** 센다. 두 가지가 여기서 갈린다.

- **큐가 비어 있으면 완료다.** "0이 두 패스 연속 그대로"는 정체가 아니다.
- **"3회 반복"도 큐 항목만 센다.** 큐 밖으로 뺀 것(레거시·기각한 오탐)은 감싼 스킬이 매 패스 다시
  보고하므로 정의상 3패스째에 3회가 된다. 신호인 것은 **고치기로 해서 실제로 고쳤는데 또 돌아온
  항목**뿐이다.

**발견의 동일성은 `파일 + 문제의 요지`로 판정한다. 라인 번호와 심각도는 키에서 제외한다** —
코드를 고치면 라인이 밀리고, 부분 수정은 심각도를 낮춘다(CRITICAL → MEDIUM). 둘 중 하나라도 키에
넣으면 같은 발견이 새 발견으로 보여 반복 카운터가 영영 올라가지 않는다.

### 분류는 패스 간에 유지한다

감싼 스킬은 기억이 없으므로 **큐는 매 패스 재구성된다.** 그런데 정체 판정은 큐 크기의 패스 간
비교다 — 재분류가 흔들리면 **유일한 수렴 지표가 흔들린다.**

**한 번 기각·범위 밖으로 분류한 발견은 새 근거가 있을 때만 재분류한다.** 바꿨으면 **그 사실과 이유를
패스 요약에 밝힌다.**

**기각 목록과 범위 밖 목록은 매 패스 요약에 다시 싣고, 다음 패스에서 그대로 재사용한다.**
파일로 남기지 않으므로 대화에만 존재하고, 요약에 실려 있어야 압축 뒤에도 그대로 재사용된다.

**수렴하지 않는 것은 실패가 아니라 신호다.** 큐가 안 줄면 접근이 틀렸다는 뜻이므로, 왜 수렴하지
않는지를 보고하고 멈춘다.

## 완료 보고

이 요약은 그대로 출력한다. 담을 항목은 `references/report-format.md`에 있다.
