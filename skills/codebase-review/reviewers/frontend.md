# Frontend Reviewer — 리뷰 지침

**이 문서는 스킬이 아니라 `codebase-review`가 dispatch한 subagent가 Read해서 그대로 수행하는
지침이다.** 사용자가 직접 부르지 않는다. 호출 방법과 입력값은 `../SKILL.md` Phase 3에 있다.

클라이언트 사이드 코드를 **네 렌즈**로 점검한다: 구조·품질 / 중복·복잡도 / 데드코드 / 성능.
코드 수정은 하지 않는다. 발견 사항만 보고한다.

**대상 프로젝트에 파일을 쓰지 않는다.** 리포트는 응답 텍스트로만 돌려준다 — 리포트를 파일로
저장하지 않고, 임시 파일도 대상 저장소 안에 만들지 않는다.

**네 렌즈를 하나로 뭉뚱그리지 마라.** 아래 "검사 순서"의 패스를 **순서대로 각각** 수행한다.
한 번 훑으면서 눈에 띄는 것만 적으면 렌즈를 나눈 의미가 사라진다 — 이 에이전트는 네 개의 독립
에이전트를 합친 것이고, 합친 이유는 **보고 중복**을 줄이려는 것이지 **검사 깊이**를 줄이려는
것이 아니다.

## 입력 계약

프롬프트로 다음을 받는다:

| 키      | 값                                                                                                          |
| ------- | ----------------------------------------------------------------------------------------------------------- |
| `mode`  | `base-diff` (기본) 또는 `full`                                                                              |
| `scope` | `backend` / `frontend` / `all` — **참고용.** 스킬이 이미 이걸로 `files`를 걸렀다                            |
| `base`  | `git diff`에 넘길 리뷰 기준 인자. revision 표현식이거나 플래그다 (`origin/main...HEAD`, `HEAD`, `--cached`) |
| `files` | 리뷰 대상 파일 목록 (`mode=base-diff`일 때만). 저장소 루트 기준 경로                                        |

**`mode=base-diff` (기본)** — `files`에 나열된 파일만 보고 대상이다.

- 판정에 필요한 문맥(부모 컴포넌트, 스토어, 타입 정의, 설정)은 코드베이스 전체를 읽어도 된다.
  **읽는 범위 ≠ 보고 범위.** 목록 밖 파일의 이슈는 보고하지 않는다(아래 데드코드 예외만 제외).
- 변경 내용이 필요하면 `git diff {base} -- {files}`로 본다. `files`는 **파일 목록이지 diff가 아니며**,
  리뷰 단위는 변경된 파일 **전체**다.
- `files`가 비면 "대상 없음"을 보고하고 즉시 종료한다. **전체 스캔으로 폴백하지 않는다.**
- `scope`를 하드 게이트로 재검사해 스스로 종료하지 않는다 — `--domain`으로 강제 호출될 수 있고,
  그때 자체 게이트는 스킬의 도메인 필터와 충돌한다. 대상 여부는 `files`가 정한다.

**`mode=full`** — 프론트엔드 코드베이스 전체가 대상이다 (`full`에는 `files`가 오지 않는다).

**어느 모드에서든 프론트엔드 파일만 점검한다.** 대상이 하나도 없으면 "대상 없음"으로 종료한다.
`mode`가 없으면 `base-diff`로 간주한다. `mode`도 `files`도 없으면 대상 없음으로 종료한다.

## 프로젝트 규칙 로딩

**시작 시 반드시 CLAUDE.md를 읽고** 프로젝트의 프론트엔드 프레임워크, 컴포넌트 규칙, 상태 관리
라이브러리, CSS 방법론, 기술 스택을 파악한다. 프로젝트 특화 규칙이 있으면 아래 범용 항목에
**추가하여** 함께 점검한다.

**프레임워크의 현행 관용구를 기준으로 판정한다.** 이전 세대 패턴을 요구하지 않는다 — 프로젝트가 쓰는
버전의 권장 방식이 무엇인지 package.json과 실제 코드에서 먼저 확인하고, 거기에 맞춰 본다.

## 판정 기준 — 렌즈가 공유하는 것

**임계값은 눈금이지 규칙이 아니다.** 컴포넌트 300줄 같은 수치는 "여기서부터 의심하라"는 신호일 뿐이다.
**같은 코드베이스의 관행이 실질적 기준이다.** 보고할 때는 수치가 아니라 **결과**를 근거로 든다:
무엇을 이해하기 어렵게 만드는가, 어떤 변경이 어렵거나 위험해지는가.

**측정 없는 최적화는 보고하지 않는다.** 데이터·상호작용 규모에 따라 비용이 **커지는 구조**(리스트
전량 렌더, 미정리 구독, 워터폴)와 상수 시간 낭비를 구분한다. 각 성능 발견에 **무엇이 어떻게
커지는지**를 근거로 든다.

## 전역 검색이 필요한 두 렌즈

### 코드 중복 검출의 특수성

중복 판정은 **비교 대상을 찾기 위해 코드베이스 전체를 검색해야 한다**. 검색은 전역으로 하되,
`base-diff` 모드에서는 아래 두 가지만 보고한다:

- 대상 파일 **내부**의 중복
- 대상 파일이 **기존 코드와 중복**되는 경우 → 이때 보고 위치는 **대상 파일**이다.
  "이미 {기존 파일}에 동일 컴포넌트/로직 존재 — 재사용하라"로 기술한다.

### 데드코드 검출의 특수성 — 보고 범위의 유일한 예외

데드코드 판정은 **참조를 찾기 위해 코드베이스 전체를 검색해야 한다**. 검색은 전역으로 하되,
**보고 대상은 `files` 안에서 정의된 심볼로 한정**한다.

`base-diff` 모드의 질문은 "이 코드베이스에 데드코드가 있는가"가 아니라
**"이 변경이 데드코드를 남겼는가"**이다:

- 대상 파일에서 **정의된** 심볼 → 전역 검색으로 참조 0건인지 확인
- 이 변경이 **삭제한 참조** → 그 참조의 유일한 사용처였다면 대상 심볼이 고아가 된다.
  이 경우 `files` 밖에 있어도 보고한다 (**이 변경이 직접 유발한 데드코드**이므로).
  근거를 반드시 명시한다: "{대상 파일}이 마지막 참조를 제거함"

**삭제된 참조를 찾는 법:**

```bash
git diff {base} -- {files}                      # 대상 파일에서 삭제된 라인
git diff --name-only --diff-filter=D {base}     # 통째로 삭제된 파일
```

**통째로 삭제된 파일은 `files`에 없다** (스킬이 `--diff-filter=d`로 제외한다). 파일 삭제는 컴포넌트를
고아로 만드는 가장 흔한 경로이므로 위 명령으로 반드시 따로 확인한다.

**예외의 한계 — 1홉만.** 컴포넌트 A가 죽었다고 해서 A가 쓰던 B, C까지 연쇄적으로 보고하지 않는다.
전이 폐포를 따라가면 모듈 절반이 보고 대상이 되어버린다.

### 정적 검색으로 놓치는 참조

참조 0건을 곧바로 "죽었다"로 단정하지 않는다. **해당 가능성이 있으면 확신도를 낮추고 근거를 적는다.**

- 동적으로 조립되는 클래스명(`bg-${color}`)·컴포넌트명, 문자열로 지정되는 라우트
- 프레임워크 규약 기반 진입점 (파일 기반 라우팅, 라이프사이클 훅, 슬롯)
- 코드 생성기의 산출물 또는 입력, 빌드 타임에만 참조되는 심볼
- 외부 소비자가 있는 공개 API (디자인 시스템·컴포넌트 라이브러리라면 미사용 export가 곧 데드코드가 아니다)

## 패스 A — 구조·품질

### A1. 컴포넌트 구조

- 한 컴포넌트가 여러 책임을 지고 있어 분리가 필요 (눈금: 300줄 — 절대 규칙이 아니라 의심 신호)
- 과도한 props drilling
- 레이아웃/페이지/컴포넌트 역할 혼재
- 조건부 렌더링 과도 중첩

### A2. 상태 관리

- 전역 상태 남용 (로컬이면 충분한 것이 전역 store에)
- 서버 상태와 클라이언트 상태 미분리
- 파생 값을 별도 상태로 저장 (computed/derived 미사용)
- 상태 변경 시 불변성 미준수
- 상태 동기화 로직 중복

### A3. API 계층

- 컴포넌트에서 직접 fetch 호출 (API 클라이언트 미사용)
- 에러 핸들링 일관성
- API 응답 타입 정의 여부

### A4. 라우팅 / 렌더링 경계

- 라우트와 컴포넌트 책임 분리
- SSR/서버 컴포넌트 경계 위반 (브라우저 전용 API가 서버에서 실행, 클라이언트 전용 훅이 서버 경계에 노출)

### A5. 타입 안전성

- `any` 타입 사용 (근거 없는)
- Non-null assertion 남용 (`value!`)
- `as` 캐스트로 타입 체크 우회
- 외부 경계(API 응답, URL 파라미터, localStorage)의 값을 검증 없이 신뢰
- 옵셔널 체이닝으로 실제 문제를 덮는 경우
- 제네릭 타입 파라미터 미활용

### A6. 접근성 (a11y) — WCAG 2.2 기준

- 시맨틱 HTML 미사용 (div로 버튼·링크 대체)
- 인터랙티브 요소에 접근 가능한 이름 없음 (aria-label, 라벨 연결)
- 키보드로 도달·조작·탈출 불가 (포커스 트랩, 커스텀 위젯)
- **포커스 표시가 보이지 않음** (WCAG 2.2 신설: Focus Not Obscured / Focus Appearance)
- **탭 순서만으로 반복 도달해야 하는 UI** (Focus Order, 드래그 전용 조작 — 대체 수단 필요)
- 이미지 alt 텍스트 누락, 색상만으로 정보 전달, 색상 대비 부족
- 폼 오류를 시각적으로만 표시 (스크린리더에 미전달)

### A7. 프레임워크 패턴 준수

- 프레임워크 권장 패턴 미사용 (CLAUDE.md 및 사용 중인 버전 기준)
- 이펙트/생명주기 훅의 의존성 누락, 또는 이펙트로 처리할 필요가 없는 파생 계산
- 상태 관리 패턴 일관성

### A8. i18n

- 하드코딩된 사용자 대면 문자열
- 날짜/숫자/통화 포맷 미처리
- **운영자·개발자용 문구가 사용자 화면에 노출**(설정 누락 안내, 환경변수명, 배포 정보 등).
  다국어 화면에 한 언어의 원문만 렌더되는 경우를 포함한다

## 패스 B — 중복·복잡도

### B1. 코드 중복

- 유사한 컴포넌트 로직 반복
- API 호출 패턴 중복
- 스타일 중복

### B2. 컴포넌트 복잡도

- 한 컴포넌트가 여러 책임 (패스 A1과 겹치면 **한 번만** 보고한다)
- 과도한 조건부 렌더링 중첩

## 패스 C — 데드코드

### C1. 미사용 export

- export된 함수/변수/타입이 다른 파일에서 import되지 않음

### C2. 미사용 컴포넌트

- 컴포넌트 디렉토리에 있지만 import되지 않는 파일
- 라우트에서 참조되지 않는 페이지

### C3. 미사용 상태/스토어

- 정의되었지만 구독/참조되지 않는 상태 관리 코드

### C4. 미사용 의존성

- package.json의 dependencies 중 import되지 않는 패키지
- devDependencies 중 config/build에서 미참조 패키지

### C5. 미사용 스타일

- 정의되었지만 적용되지 않는 CSS 클래스
- 동적으로 조립되는 클래스명은 정적 검색에 안 잡힌다 — 확신도를 낮춘다

### C6. 미사용 i18n 키

- 메시지 파일에 있지만 코드에서 참조되지 않는 키
- 언어별 메시지 파일 간 키 불일치

## 패스 D — 성능

### D1. Core Web Vitals에 영향을 주는 변경

현행 지표는 **LCP**(로딩), **INP**(응답성 — 2024년 FID를 대체), **CLS**(시각적 안정성)이다.

- **LCP** — 히어로 이미지/폰트가 렌더 블로킹, 우선순위 힌트 미사용, LCP 요소의 지연 로딩,
  데이터 페치가 렌더를 막는 워터폴
- **INP** — 입력 핸들러의 긴 동기 작업, 과도한 리렌더로 메인 스레드 점유, 디바운스 없는 고빈도 이벤트
- **CLS** — 크기 미지정 이미지/임베드, 콘텐츠 로드 후 삽입되는 배너, 폰트 스왑에 의한 레이아웃 이동

### D2. 불필요한 렌더링

- 상태 변경이 불필요한 리렌더링 유발
- 대형 리스트에 key 미지정 또는 불안정한 key(인덱스·랜덤)
- 비싼 계산을 메모이제이션 없이 매번 수행
- 렌더링 내 객체/배열 리터럴 생성 (참조 안정성 미확보)

### D3. 번들 크기

- 거대 라이브러리 전체 import (tree-shaking 미활용)
- 동적 import 미사용 (초기 로드에 불필요한 코드)
- 이미지/에셋 최적화 미적용 (최신 포맷·반응형 크기 미사용)

### D4. API 호출 효율

- 동일 데이터 중복 fetch
- debounce 미적용 (검색, 자동완성 등)
- 무한 스크롤/페이지네이션 미적용 (대량 리스트)
- 클라이언트 워터폴 (직렬 의존 없는 요청을 순차 실행)

### D5. 메모리 릭

- 이벤트 리스너/타이머/구독 미정리
- WebSocket 연결 미정리
- 대형 데이터를 클로저에 캡처

### D6. 반응성 비효율

- 비싼 계산을 파생 값으로 처리하지 않음
- 대형 배열/객체를 매번 새로 생성

## 검사 순서

1. 프로젝트 파일(package.json, tsconfig.json 등)에서 프레임워크와 **버전**, 기술 스택 파악
2. **패스 A** — 컴포넌트 파일 크기 스캔, 패턴 검색(`any`, non-null assertion, 하드코딩 문자열),
   시맨틱/aria 속성 확인, 서버·클라이언트 경계 확인
3. **패스 B** — 유사 컴포넌트·API 호출·스타일 블록 비교
4. **패스 C** — export 심볼 추출 → 전역 검색으로 참조 카운트, 의존성·메시지 파일 분석
5. **패스 D** — import 구조 분석, 렌더 경로·이벤트 핸들러·구독 정리 확인

**`base-diff` 모드에서는 위 분석을 `files`의 프론트엔드 파일에 한정한다.** 전역 Glob/Grep으로
컴포넌트를 훑지 않는다. 부모 컴포넌트나 스토어는 **읽기만** 한다 — 보고 대상이 아니다.
예외는 셋뿐이다: 중복의 **비교 상대** 검색, 데드코드의 **참조** 검색, 설정 파일 **읽기**.

### base-diff 모드에서의 범위 축소

| 항목                  | base-diff 모드 처리                                                |
| --------------------- | ------------------------------------------------------------------ |
| 번들 크기 / 코드 분할 | 대상 파일의 import 문에 한정. 전역 번들 분석은 `mode=full` 전용    |
| Core Web Vitals       | 대상 파일이 렌더하는 요소·핸들러에 한정. 실측(Lighthouse 등)은 이 에이전트 범위 밖 |
| props drilling        | 대상 파일에서 시작하는 체인만. 부모/자식은 **읽어서** 깊이를 판정  |
| 전역 상태 남용        | 대상 파일이 정의/구독하는 상태에 한정                              |
| 미사용 의존성         | package.json이 `files`에 있을 때만 점검                            |
| 미사용 i18n 키        | 메시지 파일이 `files`에 있을 때만 점검                             |
| 미사용 CSS 클래스     | 대상 스타일 파일에 정의된 클래스만 점검                            |
| 고아 파일 전수 조사   | 대상 파일 자신이 고아인지만 확인 (전체 파일 스캔 금지)             |
| **데드코드 참조 검색** | **이 변경이 추가·삭제·이름변경한 심볼만.** 손대지 않은 심볼은 이번 변경이 고아로 만들 수 없다 |
| **중복 비교 상대 검색** | **이 변경이 추가한 블록만.** 기존 블록끼리의 중복은 이 변경이 만든 것이 아니다 |
| 코드 품질 지표        | 대상 파일 기준 집계. 코드베이스 전체 지표는 `mode=full`에서만 산출 |

## 같은 결함을 여러 패스가 잡으면 한 번만 보고한다

네 렌즈는 겹친다 — 컴포넌트 비대는 A1이면서 B2이고, 미정리 구독은 A7이면서 D5다.
**같은 파일·라인의 같은 결함은 하나의 발견으로 합치고, 어느 렌즈들이 지목했는지를 함께 적는다.**
심각도는 가장 높은 것을 쓴다.

## 출력 형식

```markdown
## 프론트엔드 리뷰 결과

### 위반 사항

| #   | 렌즈 | 유형 | 심각도 | 파일:라인 | 설명 | 개선 방향 |
| --- | ---- | ---- | ------ | --------- | ---- | --------- |

렌즈: 구조·품질 / 리팩토링 / 데드코드 / 성능 (복수면 `구조+성능`처럼 함께 적는다)
심각도: CRITICAL (즉시 수정 필요), HIGH (배포 전 수정), MEDIUM (개선 권장), LOW (참고)

### 프로젝트 특화 규칙 점검

CLAUDE.md에서 식별한 프론트엔드 규칙 준수 현황:

- [x/ /부분] {규칙}

### 통계

- 컴포넌트 수, 평균 크기, 대형 컴포넌트 목록
- `any` 사용 횟수, a11y 위반 수
- 안전한 삭제 후보 (확신도 HIGH인 데드코드만)

### 권장 개선

1. [우선순위순 개선 사항]
```
