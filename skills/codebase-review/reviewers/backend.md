# Backend Reviewer — 리뷰 지침

**이 문서는 스킬이 아니라 `codebase-review`가 dispatch한 subagent가 Read해서 그대로 수행하는
지침이다.** 사용자가 직접 부르지 않는다. 호출 방법과 입력값은 `../SKILL.md` Phase 3에 있다.

서버 사이드 코드를 **네 렌즈**로 점검한다: 구조 / 중복·복잡도 / 데드코드 / 성능.
언어·프레임워크 무관 범용 에이전트. 코드 수정은 하지 않는다. 발견 사항만 보고한다.

**입력값(`mode`·`scope`·`base`·`files`)과 리뷰 범위·반환 계약은 dispatch 프롬프트가 준다**
(`../SKILL.md` Phase 3). 그 프롬프트가 이 계약의 기준이다.

**패스 A→B→C→D를 순서대로 각각 수행한다.** 패스마다 아래 "검사 순서"의 산출을 채운 뒤 다음
패스로 간다. 네 렌즈는 보고를 합치려고 한 에이전트에 모은 것이고, 검사는 넷으로 나눠서 한다.

## 프로젝트 규칙 로딩

**시작 시 반드시 CLAUDE.md를 읽고** 프로젝트의 아키텍처 원칙, Critical Rules, 코딩 규칙,
네이밍 컨벤션, 기술 스택, 데이터 접근 패턴을 파악한다. 프로젝트 특화 규칙(계층 패턴, 도메인 모델
제약, 성능 제약, 특수 진입점, 코드 생성 도구 등)이 있으면 아래 범용 항목에 **추가하여** 함께 점검한다.

## 판정 기준 — 네 렌즈가 공유하는 것

**임계값은 눈금이지 규칙이 아니다.** 아래 수치(함수 50줄, 중첩 4단계, 파라미터 5개, 인터페이스
메서드 10개, 패키지 파일 20개)는 "여기서부터 의심하라"는 신호일 뿐이다. **같은 코드베이스의 관행이
실질적 기준이다** — 주변 코드가 일관되게 그 규모이고 읽는 데 지장이 없다면 보고하지 않는다.

보고할 때는 수치가 아니라 **결과**를 근거로 든다: 무엇을 이해하기 어렵게 만드는가, 어떤 변경이
어렵거나 위험해지는가, 테스트가 왜 곤란해지는가. "60줄이라 길다"는 근거가 아니다.
아키텍처도 같다 — 이탈의 **정도**가 아니라 이탈이 만드는 **결과**(변경 파급, 테스트 곤란,
책임 혼재)를 근거로 보고한다.

**측정 없는 최적화는 보고하지 않는다.** 데이터 규모에 따라 비용이 **커지는 구조**(N+1, 풀 스캔,
전량 메모리 적재, 릭)와 상수 시간 낭비를 구분한다. 후자는 핫 패스에서만 의미가 있다.
각 성능 발견에 대해 **무엇이 어떻게 커지는지**를 근거로 든다: 입력이 N배가 되면 쿼리·메모리가
몇 배가 되는가. "비효율적으로 보인다"는 근거가 아니다.

## 전역 검색이 필요한 두 렌즈

**데드코드·중복 렌즈의 검색 범위, 보고 위치, 데드코드 1홉 예외와 그 근거 문구는
`shared-lenses.md`를 읽고 따른다.**

- 마이그레이션·CLI 서브커맨드처럼 규약으로만 진입하는 심볼

## 패스 A — 구조 (아키텍처)

### A1. 계층 위반 (Layer Violation)

- 정의된 계층 구조의 단방향 의존 준수 여부 (예: handler→service→repository)
- 상위 계층이 하위 계층을 우회하여 직접 접근하는 경우
- 비즈니스 로직이 잘못된 계층에 위치 (핸들러에 DB 로직, 리포지토리에 도메인 규칙 등)

### A2. 순환 의존 (Circular Dependency)

- 패키지/모듈 간 순환 import 탐지
- 서비스 간 상호 의존 패턴

### A3. 관심사 분리

- 단일 모듈이 여러 관심사를 처리
- 외부 의존성이 도메인 모델에 침투
- 횡단 관심사(로깅, 인증 등)의 일관된 처리 여부

### A4. 인터페이스 설계

- 과도하게 큰 인터페이스 → 분리 필요 (눈금: 메서드 10개)
- 미사용 인터페이스 메서드 (패스 C와 겹치면 **한 번만** 보고한다)
- 인터페이스 정의 위치 적정성 (사용하는 쪽에 두는가, 구현하는 쪽에 두는가)

### A5. 패키지/모듈 구조

- 비대한 패키지, 의미 없는 단일 파일 패키지 과다 (눈금: 파일 20개)
- 비즈니스 로직의 적정한 격리 여부

## 패스 B — 중복·복잡도 (리팩토링)

### B1. 코드 중복

- 동일/유사 로직이 2곳 이상에 존재
- 반복되는 패턴 (에러 핸들링, 페이징, 변환 로직 등)
- 복사-붙여넣기 코드 탐지
- **우연한 중복과 진짜 중복을 구분한다.** 형태만 같고 변경 이유가 다른 코드를 억지로 묶으면
  결합만 늘어난다. 함께 변해야 하는 것만 중복이다

### B2. 함수 복잡도

- 함수가 길어 여러 책임이 섞임 (눈금: 50줄)
- 깊은 중첩 (눈금: if/for/switch 4단계)
- 파라미터 과다 → 구조체/객체로 묶기 (눈금: 5개)

### B3. 코드 스멜

- God function: 여러 관심사를 처리하는 함수
- Feature envy: 다른 모듈의 데이터에 과도하게 접근
- Primitive obsession: 반복되는 기본형 조합 → 타입 정의 필요
- Boolean 파라미터: 함수 동작을 분기하는 bool → 함수 분리

### B4. 네이밍

- 언어별 네이밍 컨벤션 위반
- 불명확한 변수명 (한 글자, tmp, data 등)
- 패키지/모듈명과 exported 이름 중복

### B5. 에러 핸들링 패턴

- 동일한 에러 래핑 패턴 반복
- 에러 무시 (반환값 미검사)
- 에러 메시지 불일치

## 패스 C — 데드코드

### C1. 미사용 exported 함수/메서드

- exported 함수가 패키지 외부에서 호출되지 않음
- 테스트에서만 사용되는 exported 함수 (unexport 가능)

### C2. 미사용 인터페이스 메서드

- 인터페이스에 정의되었지만 호출되지 않는 메서드

### C3. 고아 파일

- import/include되지 않는 소스 파일 (테스트 제외)
- 빈 파일 또는 주석만 있는 파일

### C4. 미사용 의존성

- 의존성 매니페스트에 있지만 실제 import되지 않는 패키지
- 언어별 도구: `go mod tidy -diff`, `npm prune --dry-run` 등

### C5. 미사용 상수/변수/타입

- 패키지 레벨 상수/변수 중 참조 없는 것
- 미사용 에러 정의, 타입 별칭

### C6. 레거시 코드

- 오래된 TODO/FIXME/HACK 주석 (git blame으로 날짜 확인)
- deprecated 표시되었지만 여전히 호출되는 코드
- 주석 처리된 코드 블록
- 켜지지 않는 기능 플래그 분기 (항상 false인 플래그의 반대편)

## 패스 D — 성능

### D1. N+1 쿼리

- 루프 안에서 DB 쿼리 실행
- 관련 데이터를 별도 쿼리로 가져오는 패턴 → JOIN/Preload 가능 여부
- 루프 내 개별 UPDATE → batch UPDATE 가능

### D2. 쿼리 최적화

- SELECT \* 패턴 → 필요한 컬럼만 선택
- 인덱스 없는 자주 필터링되는 컬럼 조합
- LIKE '%keyword%' → Full Text Search 미사용
- 큰 결과셋에 pagination 미적용

### D3. 메모리 사용

- 대량 데이터를 메모리에 전부 로드 (스트리밍/커서 미사용)
- 큰 구조체/객체를 값으로 전달 (참조 미사용)
- goroutine/thread/async task 릭 가능성 (취소/정리 미처리)
- 버퍼/풀 미반환

### D4. 동시성

- 불필요한 락 사용 (읽기 전용 접근에 쓰기 락)
- 비동기 작업 생성 후 정리 미흡
- 순차 await로 처리한 독립 I/O (병렬화 가능)

### D5. 직렬화

- 대형 구조체의 반복적 marshal/unmarshal
- 응답 직렬화 시 불필요한 필드 포함

### D6. 캐싱 기회

- 동일 쿼리/계산 반복 (같은 요청에서 중복 조회)
- 자주 조회되지만 거의 변경되지 않는 데이터

## 검사 순서

각 패스는 **발견 표의 행 N개 또는 "해당 없음" 명시**를 산출한 뒤 다음 패스로 넘어간다.

1. 프로젝트 파일(go.mod, package.json, Cargo.toml 등)에서 기술 스택 파악
2. 디렉토리 구조로 계층/모듈 구분 파악
3. **패스 A** — import/require 분석으로 의존성 방향 검증
   → 산출: 구조 렌즈 발견 행 N개 또는 "구조: 해당 없음"
4. **패스 B** — 파일 크기·함수 분석으로 복잡도 측정, 유사 코드 블록 비교
   → 산출: 리팩토링 렌즈 발견 행 N개 또는 "리팩토링: 해당 없음"
5. **패스 C** — exported 심볼 추출 → 전역 검색으로 참조 카운트, 의존성 매니페스트 분석
   → 산출: 데드코드 렌즈 발견 행 N개 또는 "데드코드: 해당 없음"
6. **패스 D** — 안티패턴 검색(N+1, 루프 내 쿼리, SELECT \*), 핫 패스 코드 리뷰,
   DB 스키마/마이그레이션에서 인덱스 정의 확인
   → 산출: 성능 렌즈 발견 행 N개 또는 "성능: 해당 없음"

**`base-diff` 모드에서는 위 분석을 `files`에 한정한다.** 전역 Glob/Grep으로 코드베이스를 훑는 대신
아래 표대로 검색 대상을 좁힌다. 어느 경우에도 **보고는 대상 파일에 한정**한다(데드코드 1홉 예외 제외).

**이것은 리뷰어 게이팅이 아니다** — 렌즈는 그대로 돌고 보고 범위도 그대로다. 좁히는 것은 **검색 대상**뿐이다.
`git diff {base} -- {files}`로 무엇이 추가·삭제됐는지 먼저 보고, **그 목록에만** 검색을 건다.

### base-diff 모드에서의 범위 축소

| 항목                   | base-diff 모드 처리                                                                 |
| ---------------------- | ----------------------------------------------------------------------------------- |
| 데드코드 참조 검색     | 이 변경이 **추가·삭제·이름변경한 심볼만** (`shared-lenses.md`)                       |
| 중복 비교 상대 검색    | 이 변경이 **추가한 블록만** (`shared-lenses.md`)                                     |
| 순환 의존              | 대상 파일이 **참여하는** 순환만 보고. 무관한 기존 순환은 보고하지 않는다            |
| 패키지/모듈 구조       | 대상 파일이 **속한** 모듈만 평가                                                    |
| 계층 위반              | 대상 파일의 import 방향만 검증 (호출 상대 파일은 읽어도 보고 대상이 아니다)         |
| 미사용 의존성          | 매니페스트(package.json, go.mod 등)가 `files`에 있을 때만 점검                      |
| 고아 파일 전수 조사    | 대상 파일 자신이 고아인지만 확인 (전체 파일 스캔 금지)                              |
| 오래된 TODO/FIXME      | 대상 파일 내의 것만. `git blame`으로 날짜 확인                                      |
| 누락 인덱스            | 대상 파일의 쿼리가 사용하는 컬럼에 한정. 스키마 파일은 **읽어서** 인덱스 유무 확인  |
| 캐싱 기회              | 대상 파일 내 중복 쿼리/계산에 한정                                                  |
| N+1, 메모리 릭, 동시성 | 대상 파일에서 그대로 점검 (호출 그래프는 전역으로 추적해도 보고는 대상 파일)        |
| 통계·지표              | 대상 파일 기준 집계. 코드베이스 전체 통계는 `mode=full`에서만 산출                  |

## 같은 결함을 여러 패스가 잡으면 한 번만 보고한다

네 렌즈는 겹친다 — 중복된 로직은 패스 B이면서 종종 패스 A(관심사 분리)이고, 미사용 인터페이스
메서드는 A4이면서 C2다. **같은 파일·라인의 같은 결함은 하나의 발견으로 합치고, 어느 렌즈들이
지목했는지를 함께 적는다.** 심각도는 가장 높은 것을 쓴다.

렌즈: 구조 / 리팩토링 / 데드코드 / 성능 (복수면 `구조+리팩토링`처럼 함께 적는다)

- 안전한 삭제 후보 (확신도 HIGH인 데드코드만)

### 권장 개선

1. [우선순위순 개선 사항]
